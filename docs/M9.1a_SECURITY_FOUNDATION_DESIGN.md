## **1\. Executive summary**

The system currently has **no authentication or authorization of any kind**. Verified empirically by route introspection: 11 application endpoints, **0 security dependencies, 0 security scopes, 0 app-level dependencies, 1 middleware (CORS)**. Every endpoint — including `finalize`, `unfinalize`, all three `delivery/*` transitions, and `sync-simrs` — is reachable anonymously.

Two facts raise this from a roadmap item to the top operational risk:

1. **The BC-5150 high-risk enablement means real patient data now exists.** Before `26b5396`, the fail-closed policy created no clinical rows, so "unauthenticated PHI endpoints" was a theoretical exposure with an empty result set. It is no longer theoretical.  
2. **`GET /api/results` requires no parameters.** A single unauthenticated request returns up to 100 records per page carrying `nomor_rm`, `nama_lengkap`, `tanggal_lahir`, `jenis_kelamin` **plus clinical values**, across all patients, with full pagination. This is the single most severe finding.

The architecture is unusually well-prepared for this work. The frontend routes every HTTP call through **one function** (`request<T>` in `client.ts:22`), already uses React Context (`ToastProvider`), and has no router to retrofit. The backend has a clean router mount point and consistent `HTTPException(status_code, detail)` conventions. The Integration Service is a **separate process writing directly via SQLAlchemy** — adding API authentication cannot break instrument ingestion.

**The blocking issue is not technical, it is governance: OD-1 (the RBAC model) is explicitly unresolved.** The task list records Option B as *"the recommendation, not an owner decision"* and states it *"must not be implemented as settled until confirmed."* Six of the eleven endpoints change permission depending on that answer.

**Verdict at time of writing: NOT READY — OPEN DECISIONS REMAIN.** Five decisions needed owner sign-off (§15). Four of the five had a clear recommendation and could be settled in one sitting; OD-1 was the only one that genuinely required the owner. **This has since been resolved, and M9.1a has since been implemented and verified — see the Governance Update and the Implementation & Verification Record following the header block.**

### **2.1 The CORS configuration is worse than it appears — \[RISK\]**

I read the installed Starlette 0.46.2 `CORSMiddleware` source rather than reasoning from memory. The current configuration produces three distinct behaviours:

| Request shape | Actual response | Consequence |
| ----- | ----- | ----- |
| Cross-origin, no cookie | `Access-Control-Allow-Origin: *` | **Any website an analyst visits can read every endpoint's response.** Since nothing requires auth today, that is a complete PHI read primitive from any origin. |

The second row is the one that matters for design: **the current CORS config is a loaded trap for cookie-based authentication.** It is a direct argument for the Bearer-token recommendation in §6.

## **6\. Authentication architecture — \[DESIGN\]**

### **6.1 Mechanism: JWT Bearer access token, no refresh token**

| Option | Assessment |
| ----- | ----- |
| **JWT access token, `Authorization: Bearer`** | **Recommended.** Stateless, no server session store, immune to CSRF (not automatically attached by the browser), and — decisively — **it does not interact with the CORS trap in §2.1** |
| Session cookie | Rejected for this codebase. `httpOnly` resists XSS, but the current CORS config would authorize credentialed cross-origin requests **from every origin**, and cookies require CSRF protection the project has none of. Two new failure modes to gain XSS resistance that §6.5 shows is already low here |
| JWT \+ refresh token | Rejected. Refresh rotation, reuse detection and a revocation store are real complexity for a single-shift on-prem workstation. An 8-hour token spans a shift |
| API keys only | Rejected for humans — no per-user identity, so NFR-08 becomes unsatisfiable |

### **6.2 Concrete parameters**

| Parameter | Recommendation | Why |
| ----- | ----- | ----- |
| Library | **PyJWT** (pinned) | Actively maintained, minimal. `python-jose` is unmaintained. Neither is installed today |
| Algorithm | **HS256** | One issuer, one verifier, one process. RS256 adds key management for no benefit here |
| Claims | `sub` (user id, string), `iat`, `exp` — **and nothing else** | See §6.3 |
| Lifetime | **8 hours**, from `ACCESS_TOKEN_EXPIRE_MINUTES` (default 480\) | One login per shift |
| Refresh | **None** | Expiry → re-login |
| Logout | **Client-side discard** | Honest semantics: the token stays cryptographically valid until `exp`. Immediate revocation is delivered by §6.3 instead |
| Validation | Signature, `exp`, `sub` presence, and `sub` resolves to an **active** user | Rejects forged, expired, malformed and orphaned tokens |
| Clock | `datetime.now(timezone.utc)`, no leeway | Single server; token times are UTC-aware and **independent of the DB's naive `TIMESTAMP` convention** |
| Failure | `401` invalid/missing/expired token · `403` authenticated but wrong role · single generic message for bad credentials | Matches the existing `{"detail": …}` convention; no enumeration oracle |

### **6.3 Authorize from the database row, not the token claim**

**Do not put `role` in the token.** The `require_role` dependency should read the live `User` row that `sub` resolves to, and authorize from `user.role` and `user.is_active`.

This buys three properties for the cost of one indexed primary-key lookup per request (negligible — every endpoint already opens a session and runs queries):

1. **Disabling an account takes effect on the next request**, not in up to 8 hours. This is the revocation story, and it is why no token blacklist is needed.  
2. **A role change takes effect immediately.**  
3. **A forged or stale `role` claim cannot escalate privilege**, because no code path reads one.

It also removes the "two sources of truth" ambiguity that a role claim plus a DB row would create.

### **6.4 Required configuration**

| Variable | Default | Behaviour |
| ----- | ----- | ----- |
| `JWT_SECRET_KEY` | **none** | **The application must refuse to start if unset or empty.** No default, no dev fallback, no auto-generation (an auto-generated per-process secret silently invalidates every token on restart) |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `480` | Explicit and configurable, per the task list bullet |
| `JWT_ALGORITHM` | `HS256` | Pinned; never read the algorithm from the token header |
| `CORS_ALLOW_ORIGINS` | **`[]`** | Fail closed — see §9 |

Added to the existing `Settings` class in `app/core/config.py`; no new configuration mechanism. **Credentials and tokens must never be logged** — this needs stating because `app/integration/` still uses `print()` (M9.5) and `sync-simrs` returns `simrs_error` verbatim.

### **6.5 On token storage in the browser**

I checked the frontend for XSS sinks: **no `dangerouslySetInnerHTML`, no `innerHTML`, no `eval`**, and exactly two runtime dependencies (`react`, `react-dom`). React escapes by default. The realistic XSS risk is therefore low, which makes `sessionStorage` an acceptable trade — see §12 for the full comparison.

## **7\. Authorization architecture — \[DESIGN\]**

### **7.1 Deny by default, enforced at the router mount**

**Recommendation: every endpoint requires authentication by default; public endpoints are an explicit, short allowlist.** The brief asked for the design safest against *future accidental exposure*, and opt-in protection fails that test — a developer adding a router in six months gets an unprotected endpoint by omission, which is precisely how all 11 current endpoints came to be open.

app.include\_router(api\_router, prefix="/api", dependencies=\[Depends(get\_current\_user)\])

app.include\_router(auth\_router, prefix="/api/auth")   \# login only — no dependency

&nbsp;

A new endpoint added to any existing router under `/api` is **protected by construction**. Making something public requires deliberately mounting it outside that dependency, which is visible in review.

### **7.2 The control that actually prevents regression**

Add a test that enumerates `app.routes` and asserts every route not in an explicit `PUBLIC_ROUTES` constant carries an auth dependency. I verified this introspection works against the live app (`route.dependant.dependencies`, `route.dependant.security_requirements`) — the technique used to produce §3 is directly reusable as a test.

**This turns "someone accidentally exposed an endpoint" into a build failure**, and it directly discharges the task list's bullet: *"a check that no endpoint outside an explicit public allowlist is reachable anonymously."* It is the highest-value single item in M9.1a.

### **7.3 Role checks**

A small dependency factory, not scattered string comparisons — discharging *"represent roles explicitly rather than as scattered string checks"*:

class Role(str, Enum):        \# app/core/security.py

    ANALYST \= "ANALYST"

    ADMIN   \= "ADMIN"

&nbsp;

def require\_role(\*allowed: Role) \-\> Callable:   \# returns a FastAPI dependency

&nbsp;

Applied per endpoint on the six clinical mutations only. **Under Option B every authenticated user passes those six**, so `require_role` would be used only on user-management endpoints — an argument for implementing the factory regardless, so Option A remains a one-line-per-endpoint change if the owner chooses it.

A full permission-matrix abstraction for 11 endpoints would be over-engineering. An enum plus one dependency factory is proportionate.

### **7.4 Layering**

Authorization belongs in the **router layer** (`Depends`), not the service layer. The services (`TestRunService`, `overview_service`) stay free of HTTP and auth concerns, consistent with the current architecture and with how `run_integration.py` reuses `repository.process_message` outside any request context.

## **8\. Password / credential design — \[DESIGN\]**

### **8.1 Hashing: Argon2id via `argon2-cffi`**

**`passlib` is not viable on this project.** Verified: Python 3.13.7, and `import crypt` → `ModuleNotFoundError` (removed in 3.13). Passlib's handler registry depends on it.

`argon2-cffi 25.1.0` is importable today — but **only incidentally**, from the global Python environment via the Jupyter stack. There is no virtualenv (`sys.prefix == sys.base_prefix`). **It must be pinned in `requirements.txt` explicitly**, not relied upon. `bcrypt` (used directly, not through passlib) is an acceptable alternative; `hashlib.scrypt` is available but requires hand-managing salts, parameters and encoding — not recommended.

### **8.2 Minimum user model**

| Field | Type | Constraint | Required? |
| ----- | ----- | ----- | ----- |
| `id_user` | `int` PK autoincrement | SERIAL | **Required** |
| `username` | `String(50)` | **NOT NULL, UNIQUE** | **Required** |
| `nama_lengkap` | `String(100)` | NOT NULL | **Required** — display name and audit legibility |
| `password_hash` | `String(255)` | NOT NULL | **Required** — sized for Argon2id encoded output |
| `role` | `String(20)` | NOT NULL | **Required** |
| `is_active` | `Boolean` | NOT NULL, `server_default=text("true")` | **Required** — the revocation mechanism (§6.3) |
| `created_at` | `TIMESTAMP` | NOT NULL, `server_default=func.current_timestamp()` | **Required** |
| `last_login_at` | `TIMESTAMP` | nullable | **Optional** — useful for dormant-account review |

**No email field.** The PRD requires none, password reset is out of scope, and an on-prem lab server has no mail path. Storing an identifier with no consumer is unjustified data.

**`role` as `String(20)` validated in the application, not a DB `CHECK`.** The schema currently contains **zero CHECK constraints**, and `delivery_status` / `connection_status` are already app-level enums stored as VARCHAR. Following the convention is correct; adding the schema's first CHECK constraint for this is a gratuitous deviation. *Trade-off, stated honestly: an invalid role could be written by direct SQL. Mitigated by parsing `Role(user.role)` on read and failing closed.*

### **8.3 Required vs deferred**

| Item | Status |
| ----- | ----- |
| Argon2id hashing; plaintext never stored or logged | **REQUIRED** |
| `username` uniqueness at the DB level | **REQUIRED** |
| `is_active` gate checked on every request | **REQUIRED** |
| Minimum password length (≥12) enforced at creation | **REQUIRED** |
| Admin-only account creation | **REQUIRED** (see §10) |
| Self-service password change | **REQUIRED — OD-S4 resolved: INCLUDE in M9.1a**, current password must be verified |
| Password reset / recovery flow | **DEFERRED** — no mail path; admin re-sets the password |
| Password complexity rules, rotation, history | **DEFERRED** — modern guidance favours length over composition |
| Account lockout / login throttling | **DECIDED — OD-S5 resolved:** fixed \~1s delay on failed login; no account lockout |
| Email, MFA, external IdP, self-registration | **OUT OF SCOPE** |

## **9\. CORS design — \[DESIGN\]**

**Current: `allow_origins=["*"]`, `allow_credentials=True`, `allow_methods=["*"]`, `allow_headers=["*"]` — see §2.1 for what this actually does.**

There is **no Vite proxy** (`vite.config.ts` has only the React plugin), so the browser genuinely makes cross-origin requests from `:5173` to `:8000`. CORS is load-bearing, not cosmetic.

| Setting | Proposed | Rationale |
| ----- | ----- | ----- |
| `allow_origins` | **Explicit list from `CORS_ALLOW_ORIGINS`, comma-separated; default `[]`** | Fail closed. An unset variable must mean *no cross-origin access*, never `*` |
| `allow_credentials` | **`False`** | Bearer tokens travel in a header; credentials mode is unnecessary, and disabling it removes the §2.1 reflection hazard permanently |
| `allow_methods` | `["GET", "POST", "OPTIONS"]` | The only methods that exist |
| `allow_headers` | `["Authorization", "Content-Type"]` | Minimum for Bearer \+ JSON |
| `max_age` | default (600) | No reason to change |

**Multiple origins are expected** and the list form handles them: the dev origin (`http://localhost:5173`), and the deployed frontend origin. **Wildcard subdomains must not be used.**

**Coupled change:** `frontend/src/api/client.ts:18` hardcodes `API_BASE_URL = "http://localhost:8000"`. It should read `import.meta.env.VITE_API_BASE_URL` with the localhost value as the dev default — otherwise the deployed frontend cannot reach a non-localhost API, and the allowlist cannot be configured meaningfully. This is small and belongs with the CORS change.

**RESOLVED — OD-S2.** `/docs`, `/redoc` and `/openapi.json` expose the complete API shape including every PHI-bearing path. Owner-confirmed: **disable in production via `docs_url=None, redoc_url=None, openapi_url=None` when an `ENVIRONMENT` setting is `production`**, keep them in development. `/health` is the only endpoint public in every environment. Low severity on an intranet, trivial to implement, and it removes a reconnaissance aid.

## **10\. Database / migration impact — \[DESIGN\]**

### **10.1 Minimum schema addition**

**One new table: `users`.** No other schema change is required by M9.1a. No existing table is altered — attribution columns belong to **M9.1b**.

`04_DATABASE_DESIGN.md` contains **no user table anywhere** (verified by search), and §32 "Final Schema Summary" is marked *"Final untuk menjadi acuan database architecture LIS MVP"*. **This is a genuine documentation gap, not an oversight in my reading** — see §17.

`users` is unambiguously **Workflow Metadata**, not Clinical Data (§25), and does not make LIS a patient-identity source of truth (§26). The design boundary is respected.

### **10.2 Conventions the migration must follow — \[IMPL\]**

Derived from `visits` / `test_runs`, the two tables M1 created:

* `id_user: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)` → **SERIAL**, matching the whole schema. **Not `Identity`** — the M9.0 fidelity rule  
* `TIMESTAMP` without time zone  
* `server_default=func.current_timestamp()` for `created_at`; `server_default=text("true")` for `is_active`  
* Named constraints (`uk_`, `idx_` prefixes) where explicit constraints are declared  
* `from __future__ import annotations`, `Mapped[...]`, registered in `app/models/__init__.py` and `__all__`

### **10.3 Migration placement**

A single new revision **appended after the current head `4aff9e134f16`**. The chain becomes:

8e973e84a9d7 (R0) → b1f9dbe772fa → 4a24240f8c32 → 621889e316b5 → c5465739f048 → 4aff9e134f16 → \<users\>

&nbsp;

Single root, single head preserved. This applies cleanly to **all three live provisioning paths** in `04_DATABASE_DESIGN.md` §29 — fresh install (29.1), legacy stamp-then-upgrade (29.2), existing dev (29.3) — and does not touch the stable PoC (29.4), which stays out of the migration lifecycle entirely.

### **10.4 ⚠ Do not autogenerate this migration — \[RISK\]**

I verified the two known drifts against the ORM:

* **F-2:** `patient.py:16` declares `nomor_rm` with `unique=True`; the chain does not create it → **autogenerate would ADD `UNIQUE(patients.nomor_rm)`**  
* **F-3:** the four M8.4 indexes exist in `4aff9e134f16` but in **no ORM model** → **autogenerate would DROP all four**

So `alembic revision --autogenerate -m "users"` would emit the `users` table **plus an unapproved F-2 remediation plus the removal of four query-performance indexes**. The M9.0 investigation deliberately excluded F-2 from R0 as a separate remediation.

**The `users` migration must be hand-authored, or autogenerated and then stripped to the `users` table alone.** Its `downgrade()` must be a real `op.drop_table("users")` and must be tested — F-4 (the broken `b1f9dbe772fa.downgrade()`) exists precisely because a downgrade path was never exercised.

**F-2, F-3 and F-4 remain separate remediations. M9.1a must not resolve, fold in, or worsen any of them.**

### **10.5 Test impact — expected, must be deliberate**

`backend/tests/test_migration_chain.py` asserts the head schema by **exact equality**. A `users` table breaks these, by design — that test exists to catch unintended drift:

| Line | Assertion | Effect |
| ----- | ----- | ----- |
| `:516` | `snap.tables == _FINAL_TABLES` | 11 → 12 |
| `:517` | `snap.sequences == _FINAL_SEQUENCES` | 11 → 12 (`users_id_user_seq`) |
| `:523` | `count("p") == 11` | → 12 |
| `:524` | `count("u") == 5` | → 6 (`username`) |
| `:525` | `count("f") == 10` | unchanged — `users` has no FK |
| `:526` | `count("c") == 0` | unchanged **if** role is VARCHAR (§8.2) |
| `:527` | `len(not_null_columns()) == 41` | increases |
| `:528` | `len(index_names()) == 21` | increases (PK \+ UNIQUE backing) |

**The replacement numbers must be derived from the actual migration output, never estimated** — that is the entire point of the test. The `_FINAL_TABLES` / `_FINAL_SEQUENCES` sets are updated by adding the new members, not by loosening the equality to a subset check.

The API/ingestion tests use `Base.metadata.create_all()`, so `users` appears automatically there — **no change needed**.

## **11\. First-admin bootstrap — \[DESIGN\]**

### **11.1 Mechanism: a dedicated operator CLI script**

**Recommendation: `backend/scripts/create_admin.py`**, following the established `seed_master_data.py` pattern (`sys.path` setup, `SessionLocal`, and — notably — an explicit **database safety check** that aborts on the wrong target).

py scripts/create\_admin.py \--username \<name\>

   → prompts for the password twice via getpass (never echoed, never in argv)

&nbsp;

| Requirement | Design |
| ----- | ----- |
| Fresh install (§29.1) | Run after `alembic upgrade head` |
| Legacy install (§29.2) | Run after `stamp` \+ `upgrade head` — identical procedure |
| Existing dev (§29.3) | Identical |
| Stable PoC (§29.4) | **Never run** — that database is not in the migration lifecycle |
| Repeat prevention | **Refuses if any ADMIN already exists**, unless `--force` is passed explicitly |
| Password input | `getpass` prompt, confirmed twice, minimum length enforced |
| No admin exists | The system is **locked** — deny-by-default means nobody can log in. **This is the correct failure mode.** Never fall back to open access; never auto-provision |

### **11.2 What the bootstrap must not be — \[RISK\]**

* **Not a migration.** A migration seeding an admin would install a **known credential on every deployment**, including every legacy upgrade (§29.2), and it would be replayed identically on the dev database. This is the single worst available design.  
* **Not an application-startup auto-create.** Same known-credential problem, and it makes "no admin" silently self-healing rather than visibly blocking.  
* **Not an env-var password in the default path.** `ADMIN_PASSWORD=…` leaks into shell history, `ps` output, systemd units and container inspect. *If a non-interactive path is later needed for automated provisioning, add it as an explicit opt-in flag with a documented warning — but the default must be the interactive prompt.*

The bootstrap operator already needs database and filesystem access on the server, which is inherently more privileged than any API role. The script grants no authority they do not already have.

## **12\. Frontend auth design — \[DESIGN\]**

### **12.1 Current architecture — \[IMPL\]**

| Aspect | State |
| ----- | ----- |
| Router | **None.** `react` \+ `react-dom` are the *only* runtime dependencies |
| Navigation | `useState` \+ conditional rendering inside `App.tsx` |
| Global state | **React Context already in use** — `ToastProvider` wraps `<App/>` in `main.tsx` |
| Fetch layer | **One chokepoint**: `request<T>()` at `client.ts:22`. Every call goes through it |
| Error type | `ApiError` already carries `.status` — a 401 is distinguishable today |
| Test tooling | None (M9.4 item 5\) |
| Login UI spec | **None.** `05_DESIGN_SYSTEM.md` has no login guidance; M8.5 explicitly scoped auth out |

### **12.2 Smallest compatible architecture**

**No new dependency. No router. No state-management library.**

1. **`AuthProvider`** (React Context) wrapping `<App/>` in `main.tsx`, beside `ToastProvider` — the pattern the codebase already uses. Holds `{ user, token, login, logout }`.  
2. **`LoginView`** — a gate in `App.tsx`, not a route: `if (!token) return <LoginView />`. This is exactly how `App.tsx` already switches between detail, search and overview views. **Adding a router purely for `/login` would be unjustified.**  
3. **`client.ts` — two changes, both in the one chokepoint:**  
   * attach `Authorization: Bearer <token>` when a token is present  
   * on **401**, clear the token and surface unauthenticated state → the UI falls back to `LoginView` automatically  
4. **Token storage: `sessionStorage`.** Survives reload (a clinical workstation reloads often), clears on tab close, and is per-tab. XSS risk is the trade-off — mitigated by the verified absence of XSS sinks and the two-dependency surface (§6.5). *In-memory-only is safer but forces re-login on every refresh; `localStorage` persists across browser restarts on a shared workstation and is worse for this environment.*  
5. **Expiry handling:** no proactive timer. The next 401 triggers logout with a clear "session expired" message. Simple, and correct even if the clock drifts.

**M10.1 interaction:** the task list already records that if auto-refresh consumes a protected endpoint, the refresh path must handle auth and token expiry. Because both concerns live in `request<T>()`, **M10.1 inherits this for free** — a background refresh hitting a 401 logs out through the same path. No coordination needed beyond keeping the logic in the client.

## **13\. M9.1b compatibility**

M9.1b must record the acting user on finalize, unfinalize, delivery transitions and sync-simrs, **and that attribution must not be spoofable by the caller**. Three design rules in M9.1a keep that door open:

1. **`get_current_user` returns the ORM `User` object, not just an id.** M9.1b then has `current_user.id_user` available at every router without a second lookup.  
2. **Pass the actor explicitly down to the service layer.** When M9.1b arrives, `TestRunService.finalize_run(db, run_id)` becomes `finalize_run(db, run_id, actor)`. **Do not introduce a contextvar, thread-local or request-global "current user" in M9.1a** — implicit ambient identity is hard to test and makes the attribution path invisible at the call site. An explicit parameter is the design that does not paint M9.1b into a corner.  
3. **Identity comes only from the validated token.** No endpoint may accept a `user_id` from a body, query or header. Because `sub` is signature-verified and then resolved against a live active row, attribution is non-spoofable **by construction** — which is precisely what M9.1b's third bullet requires.

**A constraint worth stating plainly: M9.1a alone does not satisfy NFR-08.** NFR-08 requires audit information to include *"identitas pengguna"*. M9.1a establishes identity; **M9.1b records it**. Both are gates in every posture. Under Option B, M9.1b is the *only* remaining NFR-08 control — which is why OD-1 and M9.1b's priority are the same decision.

## **19\. Risks and trade-offs**

| \# | Risk | Severity | Mitigation |
| ----- | ----- | ----- | ----- |
| 1 | **Autogenerating the users migration silently adds F-2 and drops four M8.4 indexes** | **High** | Hand-author; review the diff object by object (§10.4) |
| 2 | Migration-chain test count updates done by estimation rather than measurement | **High** | Derive from actual output; the test's purpose is to catch drift |
| 3 | An endpoint added later without auth | **High** | Deny-by-default mount \+ the enumeration test (§7.2) |
| 4 | **`JWT_SECRET_KEY` defaulted, weak, or committed** | **High** | No default; refuse to start; `.env` stays gitignored; `.env.example` carries a placeholder only |
| 5 | **A migration or startup path seeding a known admin credential** | **High** | Bootstrap is an interactive CLI only (§11.2) |
| 6 | **Plain HTTP exposes tokens and PHI on the LAN** | **Medium–High** | **OD-S6 — owner decision, no repository requirement exists today** |
| 7 | Existing API tests break when auth lands | Medium | Expected; a shared auth fixture. **This is exactly the M9.4 dependency** |
| 8 | 8h token cannot be revoked cryptographically | Medium | Per-request `is_active` check gives immediate disable (§6.3) |
| 9 | `sessionStorage` token readable by XSS | Medium | No XSS sinks verified; two runtime deps. **Accepted trade-off** — alternatives cost a re-login per refresh or a CSRF surface |
| 10 | `argon2-cffi` present only incidentally in a global Python env | Medium | Pin in `requirements.txt`; **a virtualenv would be a genuine improvement (out of M9.1a scope)** |
| 11 | Option B removes role-based separation of duties | Medium | **M9.1b becomes mandatory.** Option A's alternative — shared credentials — is worse |
| 12 | **FR-17/AC-12 stay formally unmet** | Medium | OD-S3; already externally blocked via RG-2; endpoint is safer closed |
| 13 | Frontend error messages echo backend bodies | Low | Generic auth errors server-side; consider trimming `client.ts:41` |
| 14 | Login view has no design-system precedent | Low | Reuse existing tokens; §17 optional doc item |
