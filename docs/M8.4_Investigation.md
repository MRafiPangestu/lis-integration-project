## **3\. Row Grain Decision**

**One overview row \= one Order, scoped to the requested instrument.**

**Rejected alternatives:**

* **Patient** — a patient may legitimately have many visits/orders (schema: `Visit.id_pasien` is N:1). A patient-grained row would have to aggregate across orders, and there is no defined rule for which order's finality or delivery state wins. It also cannot drill down: M7's detail view is entered by *order* (`getOrderTestRuns(orderId)`, `frontend/src/api/endpoints.ts:22-24`).  
* **Visit** — currently 1:1 with Order in ingested data (`repository.py:171-175`), so it adds a level with no discriminating power, while the schema permits 1:N and would silently break the grain later.  
* **TestRun** — would emit one row per re-run. An order with three runs would appear three times, which defeats the purpose of an operational worklist and makes "final" meaningless per row.

**Reasoning:** Order is the entity that *owns* the invariants the overview reports. The partial unique index `idx_unique_final_run_per_order` scopes finality to `id_order`. `finalize_run` conflict-checks by `id_order` (`test_run_service.py:29-34`). `get_runs_by_order` is the drill-down API. Delivery is only reachable through a final run, which is order-scoped. Order is therefore the natural unit of both the invariant and the workflow.

**Answers to §B:**

1. Patient × Order. 2\. Yes — schema permits it; `Visit.waktu_kunjungan` has no uniqueness. 3\. Schema: yes. Current ingestion: no (one Order per Visit). 4\. Yes — that is what re-runs are. 5\. A re-run creates a new TestRun with `run_sequence = MAX+1`; results are never overwritten. 6\. Order (via the partial unique index). 7\. TestRun, reachable only when final. 8\. Order.

**Pagination implication:** paginating on Order yields exactly one row per order with no fan-out, so `COUNT(*)` and `LIMIT/OFFSET` are both correct without `DISTINCT`. This is the property that makes the query safe (§11).

## **4\. Latest Run Semantics**

**`run_sequence` is trustworthy — but it is not the right primary selector.**

| Question | Answer | Evidence |
| ----- | ----- | ----- |
| Populated consistently? | Yes | `repository.py:177` on every ingest |
| Where assigned? | `_next_run_sequence` \= `COALESCE(MAX(run_sequence),0)+1` | `repository.py:45-52` |
| Monotonic per Order? | Yes | MAX+1 \+ `UniqueConstraint(id_order, run_sequence)` |
| Can be NULL? | **No** — `Integer, nullable=False` | `models/test_run.py:44` |
| Duplicates possible? | **No** — DB-enforced per order | `b1f9dbe772fa:49` |
| Is `waktu_run` sufficient? | **No** — column is nullable, and it is the instrument clock (a wrong device clock reorders runs) | `models/test_run.py:45` |

**RECOMMENDATION — define an *effective run*, not a "latest run":**

ORDER BY is\_final DESC, run\_sequence DESC, id\_run DESC   →  take first

**Why this and not "latest by run\_sequence":** M7 already selects the displayed run with exactly `is_final DESC → run_sequence DESC → waktu_run DESC → id_run DESC` (`App.tsx:67-83`). If the overview reports the *latest* run while the detail view opens the *final* run, the abnormal count and delivery state shown in the list will not match what the user sees after clicking. **This is a correctness requirement, not a preference.**

`waktu_run` is deliberately omitted from the server-side rule: it is nullable, and `run_sequence` is a strictly stronger monotonic key within an order. Since `(id_order, run_sequence)` is unique, `run_sequence DESC` is already deterministic; `id_run DESC` is a defensive tie-breaker only.

## **5\. Finality Semantics**

1. **Yes** — `is_final = TRUE` means "this run is the clinically selected run for its order." Only `finalize_run` sets it (`test_run_service.py:42`).  
2. **Yes, enforced at DB level** — partial unique index on `(id_order) WHERE is_final = TRUE`, with an application-level pre-check for a cleaner 409 (`test_run_service.py:29-39`) and an `IntegrityError` fallback (`:46-51`).  
3. **No final run is the normal state**, not an error. Ingestion always writes `is_final=False` (`repository.py:184`), and finalisation is an explicit operator action. Under `bc5150_field_verified` no runs are created at all, so most orders in a live system will have no final run.  
4. Historical failed runs are irrelevant to finality — a `failed` run may be final or non-final (unfinalise from `failed` is permitted, `test_run_service.py:63`).

**Query rule:**

has\_final    := EXISTS(SELECT 1 FROM test\_runs t WHERE t.id\_order \= o.id\_order AND t.is\_final)  
final\_run\_id := the id\_run of that row (at most one, DB-guaranteed)

6. **The effective run** (§4) is what the overview presents. When a final run exists it *is* the effective run, because `is_final DESC` sorts it first.

1. Stored on `test_runs.delivery_status`, `String(30) NOT NULL DEFAULT 'pending'` (`models/test_run.py:49-51`).

Expose it as nullable and let the UI render `null` as "not finalised". **Do not** invent a synthetic value such as `"not_applicable"` — that would add a state to a state machine the contract says not to extend.

## **7\. Abnormal Count Semantics**

**`flag_abnormalitas IS NOT NULL` is verified correct.**

2. **No empty string** — `flag_raw = fields[8].strip()` then `if flag_raw:` guards the assignment (`:105-106`).  
3. **No whitespace** — `.strip()` is applied before the truthiness check.  
4. One result per row; `UniqueConstraint(id_run, parameter_tes)` prevents duplicates within a run.

6. **Yes, re-runs will be double-counted if the query joins `results` to `orders` naively.** This is the single most likely implementation defect (§17 R3).

**Why not "all order results":** an order with three re-runs would sum abnormals across runs, producing a number that appears nowhere in the UI. **Why not "final run":** most orders have no final run, so the count would be null for the common case. ## **9\. Date Semantics**

Four candidate timestamps, all `TIMESTAMP WITHOUT TIME ZONE`:

| Field | Nullable | Origin | Suitability |
| ----- | ----- | ----- | ----- |
| `Visit.waktu_kunjungan` | No | **Instrument clock** (`repository.py:165`) — not a real admission time | Poor: misleadingly named |
| `Order.waktu_order` | No | Server `CURRENT_TIMESTAMP` at ingest | **Best** — server-controlled, never null, one per row (matches grain) |
| `TestRun.waktu_run` | **Yes** | Instrument clock (OBR-7) | Poor: nullable, device-clock dependent, N per order |
| `TestRun.created_at` | No | Server `CURRENT_TIMESTAMP` | Usable but N per order |

**RECOMMENDATION:**

1. **Filter on `orders.waktu_order`.** It is server-generated, `NOT NULL`, and exactly one value per row — so filtering cannot change the row count or interact with the effective-run selection. Operationally it answers "which orders arrived in this window", which is the worklist question.  
2. **Boundaries: `date_from` inclusive, `date_to` exclusive** (`waktu_order >= :from AND waktu_order < :to`). Half-open avoids the classic `23:59:59.999` truncation bug with microsecond-precision timestamps.  
3. **"Today"** \= `[today 00:00:00, tomorrow 00:00:00)` computed by the **caller**, not the server. The server accepts explicit bounds only.  
4. **Timezone — UNVERIFIED, REQUIRES DECISION.** The codebase is inconsistent: `test_run_service.py:121` writes `datetime.datetime.now()` (local, with leftover deliberation comments in the source), `client.py`/`instruments.py` use `datetime.utcnow()`, and server defaults use `CURRENT_TIMESTAMP` (session timezone). Since the deployment is on-premise single-site, treating all timestamps as **server-local naive** is self-consistent, but this must be stated explicitly rather than assumed. See §19 D1.  
5. **Boundary interaction:** because the filter is on `waktu_order` and the effective run is chosen *within* the matched order, an order inside the window is returned with its effective run **even if that run's `waktu_run`/`created_at` falls outside the window**. That is the correct behaviour — the row describes the order, not the run — and it must be documented so it is not later "fixed".

## **10\. Pagination Semantics**

**Follow the existing house style exactly. Do not introduce cursors.**

* **Strategy:** offset/limit, mirroring `routers/results.py:16-17,85-86`.  
* **Parameters:** `page: int = Query(1, ge=1)`, `page_size: int = Query(50, ge=1, le=100)`.  
* **Response:** `{items, page, page_size, total}` — same shape as `PaginatedResultResponse` (`schemas/clinical.py:53-57`).  
* **Ordering:** `orders.waktu_order DESC, orders.id_order DESC`.  
* **Tie-breaker:** `id_order DESC` is mandatory — `waktu_order` has a server default and multiple orders can share a timestamp, which would otherwise make page boundaries non-deterministic and cause rows to be skipped or repeated across pages.  
* **Rationale for offset over cursor:** the expected scale is one laboratory's daily worklist with a date bound already applied; deep offsets do not occur. Cursor pagination would add complexity with no MVP benefit, and the existing endpoint sets the precedent. Note for the record: under live ingestion, offsets can shift between page fetches — acceptable for a date-bounded worklist, and worth revisiting only if M9.6 auto-refresh makes it visible.

## **11\. Query Blueprint**

**Shape: one query over `orders` with lateral/correlated selection of the effective run, plus a scalar aggregate. No fan-out, no `DISTINCT`.**

BASE          orders o  
              JOIN visits v   ON v.id\_visit  \= o.id\_visit  
              JOIN patients p ON p.id\_pasien \= v.id\_pasien

INSTRUMENT    WHERE EXISTS (SELECT 1 FROM test\_runs t  
                             WHERE t.id\_order \= o.id\_order  
                               AND t.id\_instrument \= :instrument\_id)

DATE          AND o.waktu\_order \>= :date\_from  
              AND o.waktu\_order \<  :date\_to

EFFECTIVE RUN LEFT JOIN LATERAL (  
                SELECT t.id\_run, t.run\_sequence, t.is\_final,  
                       t.delivery\_status, t.delivered\_at, t.waktu\_run, t.id\_instrument  
                  FROM test\_runs t  
                 WHERE t.id\_order \= o.id\_order  
                   AND t.id\_instrument \= :instrument\_id      \-- see §19 D3  
                 ORDER BY t.is\_final DESC, t.run\_sequence DESC, t.id\_run DESC  
                 LIMIT 1  
              ) er ON TRUE

ABNORMAL      LEFT JOIN LATERAL (  
                SELECT COUNT(\*) AS abnormal\_count  
                  FROM results r  
                 WHERE r.id\_run \= er.id\_run  
                   AND r.flag\_abnormalitas IS NOT NULL  
              ) ab ON TRUE

ORDER BY      o.waktu\_order DESC, o.id\_order DESC  
LIMIT/OFFSET  :page\_size / (:page \- 1\) \* :page\_size

`COUNT(*)` for `total` reuses the BASE \+ INSTRUMENT \+ DATE clauses only — the lateral joins never change cardinality, so the count is exact without repeating them.

**Why `LATERAL` rather than window functions or a grouped CTE:** `LEFT JOIN LATERAL … LIMIT 1` expresses "the one effective run" directly, is index-friendly (it becomes an index scan \+ limit per order), and cannot fan out. A `ROW_NUMBER()` CTE over all runs would materialise every run for every order before filtering — strictly more work for the same result. A `GROUP BY` cannot express the three-key ordering rule without a self-join.

**Duplicate-row traps this shape avoids:**

| Trap | Why it is avoided |
| ----- | ----- |
| Order → N TestRuns | Semi-join (`EXISTS`) for scoping; `LIMIT 1` lateral for selection. Never a plain `JOIN test_runs`. |
| TestRun → N Results | Results are reached only inside a scalar aggregate keyed on `er.id_run`. |
| N Orders per Visit | Grain is Order, so each is a legitimate distinct row. |
| Re-runs | Counted once, via the effective run only. |
| final/non-final mixing | `is_final DESC` first in the lateral ORDER BY; at most one final exists per order (DB-enforced). |
| Orders with zero matching runs | Cannot occur — the `EXISTS` filter requires at least one. `LEFT JOIN` is defensive only. |

## **13\. Service/API Architecture**

Follow the existing three-layer shape, but correct one weakness in the precedent.

routers/instruments.py  (extend the existing prefixed router)  
        │  parses & validates query params; maps service errors to HTTP  
        ↓  
services/overview\_service.py  (new)  
        │  owns ALL business semantics: effective-run rule, finality,  
        │  delivery derivation, abnormal-count scope, date rules  
        ↓  
SQLAlchemy Core/ORM select  (inside the service, or a thin query module)  
        │  the §11 query  
        ↓  
schemas/overview.py  (new)  ← response contract only

**Responsibilities:**

* **Router** — parameter declaration and validation (`Query(..., ge=1, le=100)`), instrument existence check → 404, delegate, return. **No SQL, no business rules.**  
* **Service** — a single entry point (e.g. `get_instrument_order_overview(session, instrument_id, date_from, date_to, page, page_size)`) that builds and executes the query and returns plain rows. This is where the effective-run and abnormal-count definitions live, so M8.5 and any future consumer inherit one definition.  
* **Schemas** — a **new summary schema**, not a reuse of the M7 detail schemas (§14).

**Deviation from the precedent, deliberately:** `results.py` puts its query inline in the router (`routers/results.py:28-110`). Do not copy that. The task list explicitly asks for a service layer, and the effective-run rule must be defined in exactly one place. Also: `TestRunService` raises `HTTPException` directly (`test_run_service.py:14`) — acceptable to match house style, but the overview service should prefer returning data and letting the router raise, since the only error is "instrument not found."

**Deliberately excluded:** every clinical value (`nilai_hasil`, `satuan`, `flag_abnormalitas`, `reference_range_snapshot`), raw messages, classification fields. The overview stays strictly view-only and non-clinical; values belong to the M7 detail view.

## **17\. Top Risks**

| \# | Risk | Impact | Mitigation |
| ----- | ----- | ----- | ----- |
| **R1** | **Effective-run rule diverges from M7.** Implementing "latest by `run_sequence`" as the task list literally says means the list shows one run and the detail view opens another | Operators see an abnormal count and delivery state that change on click — a clinical-trust failure | Freeze the rule as `is_final DESC, run_sequence DESC, id_run DESC` (§4); test \#3 asserts it directly against `App.tsx:67-83` |
| **R2** | **Row fan-out from a naive join.** A plain `JOIN test_runs` or `JOIN results` multiplies rows per re-run and per parameter, corrupting both `items` and `total` | Wrong counts, wrong pagination, duplicated patients in the worklist | `EXISTS` for scoping \+ `LATERAL … LIMIT 1` for selection \+ scalar aggregate (§11); tests \#2, \#12, \#22 |
| **R3** | **Abnormal count summed across runs.** The most likely single bug, and it produces a plausible-looking number | Silent clinical misinformation — a count that appears nowhere in the UI | Count keyed strictly on `er.id_run` (§7); test \#12 is the specific guard |
| **R4** | **Instrument leakage.** Scoping via the order or visit rather than `test_runs.id_instrument` (Order has **no** instrument FK) would show another instrument's orders | Cross-instrument data exposure; breaks the premise of an instrument-scoped worklist | Semi-join on `test_runs.id_instrument` (§8); test \#13; index `(id_instrument, id_order)` |
| **R5** | **Unstable pagination / date boundary.** Missing `id_order` tie-breaker, or an inclusive `date_to`, silently skips or repeats rows | Orders vanish from the worklist without any error | `ORDER BY waktu_order DESC, id_order DESC`; half-open `[from, to)` (§9, §10); tests \#14, \#15, \#17 |

*Honourable mention:* misleading endpoint naming (§8). Not a correctness risk, but it propagates into M8.5's component names and is cheapest to fix now.
