# M8.6 INVESTIGATION — Frontend Visual Polish

**Status:** Design specification. Not implemented.
**Baseline:** `468d6b7 feat(frontend): add multi-instrument order overview (M8.5)`
**Branch:** `refactor/orm-architecture`
**Scope:** Frontend presentation only. No backend, no API, no schema, no navigation architecture.

---

## 1. Objective

Bring the M8.5 dashboard visually closer to the `poc/mindray` visual language — a navy sidebar over a light clinical workspace, denser typography, softer borders, restrained shadows — **without changing a single behaviour, contract or data grain established in M8.1–M8.5**.

M8.6 is a **restyle**, not a redesign. Every component keeps its current props, its current data, its current semantics and its current accessibility guarantees. What changes is spacing, colour, radius, weight, and the arrangement of chrome that is currently duplicated.

**The single measurable goal:** the worklist should read as a purpose-built clinical workstation, not as a generic admin dashboard built from stacked bordered cards.

### 2.2 Concrete visual defects

**D1 — Double chrome around the MRN search.**
`FilterBar` renders itself as a card (`surface` background, `1px solid --color-border`, `border-radius: 4px`, `padding: --space-3`, `FilterBar.tsx:22-30`), and `AppShell` then wraps it in *another* surface strip with its own bottom border (`AppShell.tsx:20-28`). A bordered box inside a bordered bar, both white. This is the most visible source of the "stacked cards" impression.

**D2 — Header carries no information.**
`Header.tsx:13-16` renders a static `"LIS Middleware"` / `"Dashboard"`. It occupies a full 64px-equivalent band and tells the operator nothing. Meanwhile `OverviewHeader.tsx:17` renders the active instrument name — so the page's most important context sits in the third band down, and the top band is dead weight.

**D3 — Three stacked bordered surfaces before the first row.**
`main.main-content` → `OverviewHeader` (plain) → `DateRangeFilter` (card: `surface` + border + radius, `DateRangeFilter.tsx:52-61`) → `OrderOverviewTable` (card). With the header band and search band above, an operator sees **five** horizontal bands before the first patient.

**D4 — Form-like filter presentation.**
`DateRangeFilter` uses stacked `<label>` + `<input>` columns with 0.8rem/600 labels (`:63-89`). It reads as a data-entry form, not a worklist toolbar.

**D5 — Oversized empty state.**
`EmptyState` is a card with `--space-6` (24px) padding and a 1rem `<h2>` (`EmptyState.tsx:11-25`). Rendered as a sibling of the table, an empty worklist produces a large hollow box where a table should be.

**D6 — Pagination floats detached.**
`Pagination` is a bare flex row below the table card (`Pagination.tsx:24-32`), visually unattached to the data it paginates.

**D7 — Spacing rhythm too loose for a worklist.**
`.main-content` uses `padding: var(--space-4)` (16px) with `gap: var(--space-4)`, and the overview section adds another 16px gap (`OrderOverviewView.tsx:102`). Row cells use `--space-2 --space-3` (8px/12px) — tighter than the PoC's 14px/20px — so the table is dense while its surroundings are loose. The rhythm is inverted.

**D8 — Sidebar reads as neutral grey, not navy.**
`--color-sidebar-bg: #111827` is a neutral gray-900. The PoC uses `#0F172A` (slate-900), which has a blue cast that reads as "navy" and harmonises with the `#2563EB` accent.

**D9 — Borders are heavier than the PoC.**
`--color-border: #D1D5DB` (gray-300) against the PoC's `#E2E8F0` (slate-200). Every card edge is therefore more assertive than the reference.

**D10 — No radius or shadow scale.**
Every surface uses a literal `borderRadius: "4px"`. The PoC uses an 8/10/14px scale plus a 1px ambient shadow, which is what makes its cards read as "soft panels" rather than "outlined boxes".

### 3.2 Design principles (what to actually carry over)

1. **One dark rail, one light field.** The sidebar is the only dark surface; everything right of it is a single light field. Depth comes from a 1px border plus a barely-there shadow, never from stacked outlines.
2. **Content owns one card.** The PoC's worklist is a *single* panel containing header, body and pagination footer. Filters sit *outside* it as a flat toolbar with no chrome of their own.
3. **The header states where you are.** Left: the active instrument's full name. Right: its live metadata and the primary action.
4. **Compact type, wide padding.** Small font sizes (13–14px) with generous cell padding (14×20px) — dense information, comfortable rhythm.
5. **Colour is reserved for meaning.** Grey/white dominate; blue marks the accent and interactive affordances; red/amber/green appear only as clinical or connection signals.
6. **Status is a dot plus a word.** Never a dot alone.

## 4. Design Principles for M8.6

1. **Tokens first.** Every value in §8 becomes a CSS custom property in `index.css`. No component gains a hardcoded hex, radius or shadow.
2. **Retune, don't fork.** Existing tokens change *value*; the token *set* grows by seven names only. There is no second palette.
3. **One card per content region.** The worklist is one panel. Filters are chrome-free. Nothing is a card inside a card.
4. **Chrome earns its band.** Every full-width horizontal band must carry information. Bands that only decorate are removed.
5. **Business and state semantics are frozen; component composition may change.** No business rule, state semantic, handler body, API contract, navigation behaviour or data semantic changes. Props are only ever *added*, and only as optional.
   **Presentation-level composition changes are expressly permitted** where §6 requires them — specifically: rendering `FilterBar` inside `Header` instead of its own `AppShell` band; composing `OverviewHeader` + `DateRangeFilter` as one toolbar; and rendering `Pagination` as the worklist panel's footer instead of a sibling. In each case the moved component keeps its own props, handlers and accessibility attributes verbatim; only its position in the tree and its styling change.
   Wording to apply throughout: *no business/state semantics change; component composition may change where required by the approved visual specification.*
6. **Accessibility never regresses.** `aria-current`, `scope="col"`, `role="alert"`, `aria-live`, native `<button>` controls, and icon-plus-text-plus-colour signalling all survive verbatim.
7. **The detail view inherits, it is not edited.** `OrderDetailView.tsx` and every clinical component stay untouched; they pick up the retuned tokens automatically.

### C. Top header — `Header.tsx`

New **optional** props (so the unrendered `MainLayout.tsx` still compiles):

```ts
interface HeaderProps {
  activeInstrument?: InstrumentStatusResponse | null;
  searchProps?: FilterBarProps;
}
```

- `height: 64px`, `--color-surface`, `1px solid --color-border` bottom, `padding: 0 var(--space-6)`, `flex`, `align-items:center`, `justify-content:space-between`, `gap: var(--space-4)`, `flex-shrink: 0`, **`min-width: 0`**.
- **Left**: `<h1>` 18px/600 `--color-text-primary` = `activeInstrument.nama_mesin`, falling back to `"LIS Server"`. The title container carries `min-width: 0` and the `<h1>` carries `overflow: hidden; text-overflow: ellipsis; white-space: nowrap`, so a long instrument name truncates rather than pushing the row wider. Add `title={nama_mesin}` so the full name stays available on hover.
- **Right**: `flex`, `align-items:center`, `gap: var(--space-3)`, `min-width: 0` — a metadata stack (`protokol · tipe_koneksi`, 12px/600 `--color-text-primary`, omitted when both are null; over `Last status: {last_status_at}`, 11px `--color-text-secondary`, omitted when null) followed by the search field.
- No Sync button. No Port. Both would require data the API does not provide.

**Header overflow contract (mandatory).** The header must never be the cause of page-level horizontal scrolling at any viewport width. Three rules make that structural rather than incidental:

| Width | Title | Metadata | Search |
|---|---|---|---|
| ≥1100px | Full, ellipsis only if genuinely long | Visible | `flex: 0 1 320px`, `min-width: 220px` |
| 901–1099px | Ellipsis as needed | **Hidden** (`display: none`) | `flex: 0 1 280px`, `min-width: 180px` |
| ≤900px | Ellipsis as needed, may shrink to a few characters | **Hidden** | `flex: 1 1 auto`, **`min-width: 0`** — the 280px floor is released |

- Every flex container in the header chain (`header`, the left group, the right group, the search wrapper, the `<input>`) sets `min-width: 0`. Without this, a flex item's automatic minimum size is its content width, and the 280px input will force the row wider than the viewport regardless of the parent's `overflow`.
- The `<input>` uses `width: 100%` inside its wrapper; **`min-width` is a responsive value, never a fixed 280px**.
- At ≤900px the metadata is already hidden and the search takes the remaining space after the truncated title, so the header always fits.
- `body`, `.app-container` and the main column must never gain `overflow-x: auto`. Horizontal scrolling remains confined to the worklist panel's inner scroller (§6F).
- The ≤900px sidebar behaviour is unchanged: the existing 64px icon rail. **No drawer, no hamburger, no off-canvas panel.**

### D. Search — `FilterBar.tsx`

Same props, same `onSubmit`, same `aria-label="Patient search"`, same `htmlFor`/`id` pairing. Visual change only:

- Remove the surface background, border and padding from the `<form>` (D1).
- One row: a relative wrapper (`min-width: 0`) containing an absolutely positioned 16px search glyph at `left: 12px` and an `<input>` with `padding: 8px 12px 8px 36px`, `--radius-md`, `1px solid --color-border-input`, `height: 36px`, `width: 100%`.
- **Width is responsive, not fixed.** The wrapper uses the `flex` / `min-width` values in the §6C overflow contract — `flex: 0 1 320px` at ≥1100px, `0 1 280px` at 901–1099px, and `flex: 1 1 auto; min-width: 0` at ≤900px. - The visible `<label>` becomes visually hidden (absolute 1×1) — the placeholder plus `aria-label` on the form preserve the accessible name.
- Focus ring: `border-color: var(--color-focus-border); box-shadow: 0 0 0 3px var(--color-focus-ring)` via the `.lis-input:focus` rule in `index.css` (§8). No hardcoded colour at the component level.

## 8. Colour and Token Guidance

No component file may contain a literal hex, `rgba()` or `px` radius. This applies to focus styling as well — hence `--color-focus-border` and `--color-focus-ring` below.

## 15. Final Scope Statement
