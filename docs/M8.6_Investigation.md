## Revision 2 — what changed and why

Revision 1 was written against source alone. It has now been **implemented and reviewed in a running browser**, and that review surfaced five concrete problems the source-only assessment did not capture. Revision 2 folds that feedback in. Every Revision 1 constraint the review did not contradict is carried forward verbatim.

| # | Change | Driver | Where |
|---|---|---|---|
| 1 | Sidebar starts **open**, plus a manual collapse toggle | A monitoring workstation wants the instrument list visible at startup, but operators need the width back on demand | §6B2, §9 |
| 2 | MRN search **leaves the header** for the overview toolbar | Metadata and search collide at the header's right edge (verified cause: §2.4 D11) | §6C, §6D2, §6E |

**Decisions from Revision 1 that this revision overturns** — each is marked where it occurs and summarised in §15:

- §3.3 rejected *hamburger* and *numbered pagination* outright. Both are now **adopted, adapted**. *Client-side* pagination and the rows-per-page selector remain rejected.
- §4 principle 7 ("the detail view inherits, it is not edited") is **replaced** by a two-part boundary: detail/workflow **logic** is protected; detail/workflow **button presentation** is in scope.
- §10's `App.tsx` "one line only" allowance is **widened** to hold sidebar-expansion state and the relocated search wiring.
- Risk **B8** ("`git diff` over detail paths must be empty") is **replaced** by a content-shaped gate, **B8′** (§12).

## 1. Objective

Bring the dashboard to the `poc/mindray` visual language — a navy rail over a light clinical workspace, denser typography, softer borders, restrained shadows — **without changing a business rule, contract or data grain established in M8.1–M8.5**, and with the operator ergonomics the running-UI review asked for:

- the instrument list is visible the moment the app opens, and can be collapsed at will;
- the header states *where you are*, and nothing competes with it for that band;
- patient search sits with the worklist it feeds;
- the operator can reach any page of any range, including an instrument's entire record;
- every action button in the application — worklist and detail alike — belongs to one visual system.

M8.6 remains a **restyle plus a small number of approved compositional moves**, not a redesign. No component loses a prop, a handler, or an accessibility guarantee.

**The single measurable goal:** the application should read as a purpose-built clinical workstation, not as a generic admin dashboard built from stacked bordered cards and default browser controls.

### 2.4 Revision 2 defects — D11–D15 (from the running-UI review)

Each is stated with its source-level cause, so implementation targets the mechanism rather than the symptom.

**D11 — Header metadata overflows onto the search field.**
`Header.tsx:112` gives the metadata wrapper `minWidth: 0`, while its two children carry `whiteSpace: "nowrap"` (`:119`, `:129`) and **neither the wrapper nor the children set `overflow: hidden` or `textOverflow`**. `min-width: 0` permits the box to shrink below its content width; `nowrap` then makes the text spill rather than wrap. The right-hand group is a `flex: 0 1 auto` item, so as soon as title + metadata + search exceed the header width, the metadata renders *over* the search. The crowding observed in the browser is therefore structural, not a spacing accident. The §6C overflow contract prevented *page-level* scrolling, which it was written to do; it did not constrain *intra-header* overlap.

**D12 — Search is in the wrong region.**
The MRN search feeds a worklist that sits two bands below it, yet it lives in global shell chrome and competes with instrument metadata for the same 64px strip — D11's proximate cause. A worklist tool belongs with its worklist.

**D13 — The sidebar offers no width control.**
`Sidebar.tsx:102-104` derives width solely from `useIsNarrow()`: a 64px rail below 901px, a fixed 260px at or above it, with no operator control. On the 1366×768 screens common in labs, 260px of permanently-committed chrome is expensive while reading a wide worklist.

**D14 — Pagination conveys neither position nor extent.**
`Pagination.tsx:59-86` renders Prev, a count line, and Next. The operator cannot see how many pages exist, cannot jump, and cannot return to page 1 in one action. Adequate for a one-day worklist; inadequate once `All` (§6E2) exists.

**D15 — Workflow buttons render as raw browser chrome.**
`ConfirmationDialog.tsx:123,126`, `FinalRunWorkflow.tsx:115,129` and `SimrsSyncWorkflow.tsx:102` are native `<button>` elements with **no `style` and no `className`** — they inherit the user agent's default grey bevel, visually unrelated to everything M8.6 built. Related: fifteen sites across `detail/`, `display/`, `status/` and `workflow/` still hardcode `borderRadius: "4px"`, predating the `--radius-*` scale, so detail panels carry a different corner radius from the worklist panel beside them.

> **Note on evidence.** D11–D15 originate from an operator's review of the running UI. Each has been independently confirmed against working-tree source above, so implementation does not depend on the screenshot. They are **specification defects, not optional polish.**

### 3.2 Design principles carried over

1. **One dark rail, one light field.** Depth from a 1px border plus a barely-there shadow, never stacked outlines.
2. **Content owns one card.** The worklist is a single panel — header, body, pagination footer. Filters sit outside it, chrome-free.
3. **The header states where you are.** Nothing competes with the instrument name for that band.
4. **Compact type, wide padding.** 13–14px text with 14×20px cells.
5. **Colour is reserved for meaning.** Grey/white dominate; blue is the accent; red/amber/green are clinical or connection signals.
6. **Status is a dot plus a word.** Never a dot alone.
7. ***(new)*** **Chrome the operator can reclaim.** The rail is useful by default and dismissible on demand, and the control that dismisses it is always in the same screen position.

## 4. Design Principles for M8.6

1. **Tokens first.** Every colour, radius, shadow and spacing value resolves through a CSS custom property. No component file contains a literal hex, `rgba()` or `px` radius. This applies to focus styling and to the new button system.
2. **Retune, don't fork.** Existing tokens change *value*; the token *set* grows by **sixteen** names (eleven structural + five semantic tints). There is no second palette.
3. **One card per content region.** The worklist is one panel. Toolbars are chrome-free. Nothing is a card inside a card.
4. **Chrome earns its band.** Every full-width band must carry information; chrome the operator does not currently need should be reclaimable (§3.2 principle 7).
5. **Business and state semantics are frozen; component composition may change.** No business rule, handler body, API contract, navigation behaviour or data semantic changes.
   **Approved compositional moves:** the search relocates from `Header` to the overview toolbar; sidebar expansion state lifts to `App.tsx`; `Pagination` gains derived page buttons. In each case the moved component keeps its props, handlers and accessibility attributes verbatim.
6. **Accessibility never regresses.** `aria-current`, `scope="col"`, `role="alert"`, `role="status"`, `aria-live`, `aria-invalid`, `aria-describedby`, `role="tab"`/`aria-selected`, `aria-modal`, native `<button>` controls, and icon-plus-text-plus-colour signalling all survive verbatim. New controls add `aria-expanded` / `aria-controls` where the pattern requires them.
7. ***(REPLACES Revision 1 principle 7)*** **Detail logic is protected; detail presentation is in scope.**
   - **Protected — must remain semantically identical:** handlers, effects, state machines, API calls, confirmation logic, clinical semantics, data values, navigation semantics, conditional branches, element types, and every existing `aria-*` attribute.
   - **In scope:** `className` additions and `borderRadius` literal → token substitutions, exactly as enumerated in §6L. Nothing else.
8. ***(NEW)*** **One button system.** Every action button resolves to a shared class in `index.css`. A button's *variant* encodes its role (primary / secondary / ghost); a button's *file* does not encode its appearance.

### B2. Sidebar startup state and manual collapse — **NEW (R2)**

#### Frozen behaviour

| Aspect | Decision |
|---|---|
| **Initial state on every SPA load** | **Expanded (260px).** `useState(true)` in `App.tsx`. |
| **Persistence** | **None.** No `localStorage`, no `sessionStorage`, no URL parameter. A reload always returns to expanded. This is required by "the sidebar should start open **every time** the SPA is opened", and it avoids introducing persistent client state that M8.5 deliberately does not have. |
| **Collapsed desktop appearance** | The **existing 64px icon rail** — brand tile only, dots only, names and status words via the existing `title`. |
| **≤900px** | Rail is **forced**, exactly as M8.5 froze it. The toggle is **not rendered** at this width. |
| **Derived state in `Sidebar`** | `const collapsed = isNarrow || !expanded;` — every current `isNarrow ?` branch reads `collapsed ?` instead. `useIsNarrow()` itself, its query, its listener and its cleanup are **unchanged**. |
| **Control placement** | Header, far left, before the `<h1>` — a fixed screen position that does not move when the rail toggles. |
| **Architecture** | In-flow width change. **No drawer, no overlay, no off-canvas panel, no backdrop, no focus trap, no `position: fixed` rail.** |

#### Why the 64px rail rather than the PoC's `marginLeft: -260px`

The PoC hides the sidebar entirely. Three reasons M8.6 collapses to the rail instead:

1. **This is a monitoring workstation.** The dots are live connection status. Hiding them entirely removes the one piece of information the rail exists to broadcast; the rail keeps it at a glance.
2. **One collapse mechanism, not two.** The ≤900px rail already exists and is already verified. Reusing it means the collapsed state has a single rendering path, and the brief's requirement that "existing ≤900px 64px rail behavior must remain compatible" is satisfied by construction rather than by coincidence.
3. **No layout arithmetic.** A negative-margin slide leaves an off-flow element and a transition to manage; a width change is already how `Sidebar` computes its size (`Sidebar.tsx:104`).

*If the project owner prefers a full hide, that is a one-line change to the collapsed width and should be raised before implementation — see O7.*

#### State ownership

| Concern | Owner | Note |
|---|---|---|
| `sidebarExpanded` boolean | `App.tsx` | `const [sidebarExpanded, setSidebarExpanded] = useState(true)` |
| Toggle handler | `App.tsx` | `() => setSidebarExpanded((open) => !open)` |
| Forwarding | `AppShell` | Two optional props, passed to `Header` |
| Rendering the control | `Header` | Rendered only when `onToggleSidebar` is supplied **and** `layout !== "narrow"` |
| Applying the state | `Sidebar` | New optional prop `expanded?: boolean` (defaults to `true`) |
| Narrow detection | `Sidebar` (`useIsNarrow`) and `Header` (`useHeaderLayout`) | **Both already exist.** Neither is lifted, shared or rewritten. |

`Header` already computes `layout === "narrow"` at ≤900px via `useHeaderLayout()` (`Header.tsx:13-39`), so hiding the toggle below 901px needs no new hook and no new media query.

#### Why the toggle is hidden rather than disabled below 901px

At ≤900px the rail is mandatory, so a toggle would be inert. M8.6 already rejects controls that do nothing (the PoC Sync button, §3.3); the same rule applies here.

#### Accessibility contract

```
<button
  type="button"
  onClick={onToggleSidebar}
  aria-label="Toggle instrument sidebar"   // STABLE — does not change with state
  aria-expanded={sidebarExpanded}
  aria-controls="instrument-sidebar"
>
```

- The `<aside>` in `Sidebar.tsx:107` gains `id="instrument-sidebar"`. Its `aria-label="Instruments"` is unchanged.
- **The accessible name is stable and the state is carried by `aria-expanded`.** A name that changes with state *plus* `aria-expanded` produces a redundant double announcement; one mechanism, not two.
- Native `<button>`, in natural tab order as the header's first control. No `tabIndex`, no `outline: none`.
- The glyph is an inline SVG marked `aria-hidden="true"`. No icon dependency.
- `aria-current="page"` on the active instrument is untouched in both states.
- **In the collapsed rail each instrument button's accessible name comes from its `title`** (`Sidebar.tsx:236`), because the label stack is not rendered. This is the M8.5 ≤900px behaviour, unchanged — but Revision 2 makes it reachable on desktop, so it must be verified explicitly (V21). Sonnet **may** additionally render a visually-hidden `<span>` with the name and status inside each collapsed item; this strictly strengthens the guarantee, adds no behaviour, and is optional.

#### Motion

A `transition: width .2s ease` on the `<aside>` is **permitted, not required**. If used, `index.css` must also carry:

```css
@media (prefers-reduced-motion: reduce) {
  aside, .lis-btn, .lis-page-btn { transition: none; }
}
```

No transition may be applied to `.main-content` or to the worklist panel — animating the content column while a table reflows is visually unstable.

### E2. The `All` preset — API contract mapping — **NEW (R2)**

#### What the M8.4 contract actually permits — verified

| Fact | Evidence |
|---|---|
| `date_from` and `date_to` are **required** query parameters | `backend/app/api/routers/instruments.py:48,55` — both are `Query(...)` with no default |
| Omitting either returns **422** | FastAPI required-parameter validation |
| `date_to <= date_from` returns **422** | `instruments.py:70-71` |
| The filter is half-open on a **NOT NULL** column | `overview_service.py:100-101`; `Order.waktu_order` is `Mapped[datetime.datetime]`, `nullable=False` (`backend/app/models/order.py:21-23`) |
| Ordering is `waktu_order DESC, id_order DESC` | `overview_service.py:147` |
| A matching index already exists | `ix_orders_waktu_order_id_order (waktu_order DESC, id_order DESC)` — migration `4aff9e134f16` (M8.4) |
| `page` / `page_size` are server-side, `page_size ≤ 100` | `instruments.py:58-59` |

#### Conclusion

**`All` is fully representable with no backend change.** Omitting the date parameters is **not** viable — it returns 422. The safe representation is a **presentation-level sentinel range**:

```
allRange() → ["1900-01-01T00:00", "2999-12-31T23:59"]
```

- Both strings are valid `datetime-local` values and parse to naive datetimes, matching the `TIMESTAMP WITHOUT TIME ZONE` column.
- `date_to > date_from`, so the 422 guard passes.
- `waktu_order` is `NOT NULL`, so **no order is excluded by a null bound** — the window is complete for every row the table can hold.
- The ORDER BY already matches the M8.4 index, so deep paging over a wide range stays index-supported.
- **No API contract change, no new parameter, no new endpoint, no backend edit, no migration.**

#### Semantic model (as required by the brief)

```
All  →  date_from=1900-01-01T00:00 & date_to=2999-12-31T23:59
     →  page=1, page_size=25          (server query)
     →  Next
     →  page=2, page_size=25          (next 25 rows, server query)
```

The client never holds more than 25 rows. There is no unbounded fetch, no client-side slice, no accumulation.

#### Honest naming

The preset is labelled `All`. Strictly it means *every order whose `waktu_order` falls inside a sentinel window that brackets every clinically representable timestamp.* `waktu_order` defaults to `current_timestamp()` (`order.py:22`), so a value outside 1900–2999 is not reachable in practice. This is a documented, accepted limitation, not a silent one.

#### Where the constants live

`frontend/src/components/overview/dateRange.ts` gains **one new export**:

```ts
export const ALL_DATE_FROM = "1900-01-01T00:00";
export const ALL_DATE_TO = "2999-12-31T23:59";
export function allRange(): [string, string] { return [ALL_DATE_FROM, ALL_DATE_TO]; }
```

**`toLocalInput`, `todayRange`, `yesterdayRange` and `last7DaysRange` must remain byte-identical.** This is an addition, not a rewrite. No `toISOString()`, no `Z`, no offset, no timezone conversion — the two constants are literal server-local naive strings, consistent with the module's existing convention.

Revision 1 listed `dateRange.ts` as untouchable. That is **relaxed to "additive only"**, and only for this export.

#### Page-window algorithm — frozen

```
totalPages = Math.max(1, Math.ceil(total / pageSize))
```

Derived from props that already exist (`total`, `pageSize`). **No new prop. No new API field. No client-side dataset.**

A **centred sliding window of five** pages, clamped to `[1, totalPages]`, with first and last always rendered:

1. Always render page `1`.
2. Render `…` when `windowStart > 2`.
3. Render the window: five consecutive pages centred on `page`, shifted inward at the ends so the count stays five whenever `totalPages >= 5`.
4. Render `…` when `windowEnd < totalPages - 1`.
5. Always render page `totalPages` (when `totalPages > 1`).
6. When `totalPages <= 1`, render **no** number buttons — the count line and two disabled chevrons only.

Chosen over the PoC's block-shifting algorithm (§3.3): block-shifting makes the active page jump from a block's right edge to its left edge on every fifth page, while a centred window keeps it in a stable position and always leaves page 1 and the last page one click away.

The ellipsis is a **non-interactive `<span aria-hidden="true">…</span>`**, never a button. First and last are always explicitly rendered, so no jump is hidden behind a glyph.

## 8. Colour and Token Guidance

**Sixteen new names (eleven structural + five semantic tints); five retuned values; nothing removed.**

**Token-first rule.** Every colour, radius, shadow and spacing value written or changed by M8.6 resolves through a CSS custom property. **No file in Group 1, 2 or 3 may contain a literal hex, `rgba()` or `px` radius.**

Two qualifications, both deliberate:

- `borderRadius: "50%"` is a **shape**, not a scale value (`Sidebar.tsx:263`, the status dot). It is correct as a literal and is exempt.
- Group 4 files are governed by the narrower §6L boundary — `className` additions and radius-token substitutions only. Two `rgba()` literals therefore **survive M8.6 by design**: the modal backdrop (`ConfirmationDialog.tsx:91`) and the toast shadow (`ToastProvider.tsx:71`). Tokenising them would require editing a colour value inside a protected file, which §6L forbids. They are pre-existing debt, recorded as **NB9**, and are **not** M8.6's to fix. The rule for Group 4 is therefore *introduce no new literal*, not *remove every literal*.

## 9. Responsive Behaviour

The M8.5 navigation concept is preserved: no route change, no drawer, no off-canvas panel. The only addition is an operator-controlled width for a rail that already had two widths.

### Toolbar at the three review widths

| Viewport | Toolbar arrangement |
|---|---|
| **1200px** | Row 1 title+count; row 2 search left, `All Today Yesterday Last 7 days` right, one line; row 3 From → To inline (hidden under `All`) |

- The sidebar rule is a single derived boolean: `collapsed = isNarrow || !expanded`. `matchMedia("(max-width: 900px)")`, its listener and its cleanup (`Sidebar.tsx:32-47`) are **unchanged**.
- `useHeaderLayout()` (`Header.tsx:13-39`) is **unchanged**; only what it gates changes — it no longer sizes a search field, and it now also gates the toggle.
- **Page-level horizontal overflow is forbidden at every width.** `body`, `.app-container` and the main column never gain `overflow-x`. Horizontal scrolling exists only inside the worklist panel's inner scroller.
- The header can no longer overlap itself: every metadata line truncates with an ellipsis (§6C rule 1).
- Toolbar and pagination rows wrap with `flex-wrap: wrap` rather than collapsing into a menu.
- **No drawer, no off-canvas navigation at any width.** The 64px rail is the only collapsed form.

- Fake or demo data; controls that do nothing.

- Any change inside a Group 4 file other than a `className` addition or a radius-token substitution.

## 15. Final Scope Statement

M8.6 Revision 2 changes **ten frontend files with full presentation latitude, one file additively (`dateRange.ts`), `App.tsx` within a five-item allowance, twelve detail/workflow/display/status files under a presentation-only boundary, and the task list.** It changes no business rule, no state machine, no contract, no data grain, no dependency and no backend file.

Component *composition* changes only where §6 requires it — the search moving from `Header` to the overview toolbar, sidebar expansion state lifting to `App.tsx`, and pagination gaining derived page buttons — with every moved component keeping its props, handlers and accessibility attributes verbatim.

The `All` preset is expressed **entirely within the existing M8.4 contract** as a sentinel date range. `date_from` and `date_to` remain required, `page_size` remains 25, pagination remains server-side, and no backend file is edited.

The detail view's **logic remains protected**; only `className` additions and radius-token substitutions reach it, so that the buttons an operator uses to finalize and deliver clinical results look like part of the same application as the worklist that led them there.

The PoC's architecture, data model, endpoints, instrument array, result grain, client-side pagination and business logic are **not** reintroduced in any form. Its stat cards, Sync button, Port field and info banner remain rejected because the M8.4 contract cannot supply their data. Its hamburger and numbered pagination are adopted only as **visual patterns**, reimplemented against real server-side state.

Success is: an operator opens the app to a visible instrument list they can collapse when they want the width; a header that names the live instrument without colliding with anything; a search that sits with the worklist it feeds; a date range that can be widened to everything without loading everything; pagination that shows where they are; and detail buttons that look like they belong — with the same rows, the same order, the same badges, the same accessibility and the same click behaviour as M8.5.
