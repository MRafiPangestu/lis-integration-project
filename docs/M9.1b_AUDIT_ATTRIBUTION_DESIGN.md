## **1. Executive summary**

M9.1a (`b0b9ee7`, `docs/07_TASK_LIST.md` M9.1a section — **[VERIFIED]**) established *who is calling*: every protected endpoint resolves an authenticated `User` via `get_current_user`. It deliberately did **not** record *who did what* — no workflow mutation, and no user-management action, currently carries the acting user's identity into persistent storage. `docs/M9.1a_SECURITY_FOUNDATION_DESIGN.md` §13 named this gap explicitly and left three design rules in place so M9.1b would not require a redesign: `get_current_user` returns the full `User` ORM object, not just an id; actor identity is meant to be threaded as an **explicit parameter**, never a contextvar or thread-local; and identity must come only from the validated token, never from a client-supplied field **[VERIFIED — `docs/M9.1a_SECURITY_FOUNDATION_DESIGN.md` §13]**.

**PRD NFR-08 (Workflow Auditability)** requires the system to record final Test Run selection, final-status changes, the SIMRS delivery process, delivery status and timing, parsing errors, and instrument connection disruptions — and states that audit information must include a timestamp and **user identity when the activity was performed by a user** (`docs/02_PRD.md` §NFR-08 — **[VERIFIED]**). The instrument-side items in that list (parsing errors, connection disruptions) have no human actor and are already logged structurally elsewhere (`instrument_messages`, `instruments.connection_status`); M9.1b's job is the *user-attributed* half of NFR-08 — the half M9.1a's own §13 identified as the only remaining control once OD-1 resolved to Option B, because role alone no longer distinguishes which authenticated person acted.

This investigation found **no blocking technical obstacle**. The five `TestRunService` methods that perform every clinical workflow mutation are small, each already opens exactly one transaction, and none currently accepts an actor. The `sync-simrs` endpoint already separates its database work from its outbound HTTP call into two distinct transactions — a design chosen for concurrency safety, not for audit purposes, but one that happens to compose cleanly with "two audit rows, no HTTP call inside a DB transaction" without requiring any restructuring (§8.2). Two existing test fixtures use a stub actor with `id_user = 0`, which does not exist as a row in `users` — this will need to change once an FK is added, and is called out explicitly as an implementation-boundary item (§13), not a design blocker.

**Verdict: READY FOR IMPLEMENTATION**, per the Owner Decision Record above.

## **4. Storage model (OD-B1)**

Two options were weighed.

**Option A — actor columns on existing domain tables.** Add e.g. `finalized_by_id_user`, `delivered_by_id_user` directly to `test_runs`, and similar columns to `users` for user-management actions. **[INFERRED — rejected in favour of Option B, now moot as OD-B1 is resolved, recorded for provenance only]** This would require a different actor column per action type (a `TestRun` can be finalized, unfinalized, and delivered by three different people at three different times — one row cannot hold three independent "who/when" pairs without three separate column pairs), would touch the M9.0-reconciled migration chain's core clinical tables for a workflow-metadata concern, and would leave no record of a *history* of actions — only the latest one, since `is_final` and `delivery_status` are themselves mutable fields with no versioning.

**Option B — one append-only `audit_events` table.** A single new table, entirely additive, holding one row per attributed action, referencing the affected entity generically (`entity_type` + `entity_id`) rather than adding columns to every table that can be acted upon. This is a **history**, not a set of "last actor" columns — it naturally answers both "who finalized this run" and "show me everything ADMIN X ever did," which Option A cannot answer for the second question without a separate table anyway.

**[OWNER-APPROVED — OD-B1]** Option B. No actor columns are added to `test_runs`, `users`, or any other existing table.

## **5. Scope of attributed actions (OD-B2)**

**[OWNER-APPROVED — OD-B2]** In scope:

*Clinical workflow (five actions, all through `TestRunService`):*
1. `TEST_RUN_FINALIZED`
2. `TEST_RUN_UNFINALIZED`
3. `DELIVERY_STARTED`
4. `DELIVERY_DELIVERED`
5. `DELIVERY_FAILED`

*User management (four actions, three endpoints):*
6. `USER_CREATED` — `POST /api/users`
7. `USER_DISABLED` — `PATCH /api/users/{id_user}/status` with `is_active: false`
8. `USER_REACTIVATED` — `PATCH /api/users/{id_user}/status` with `is_active: true`
9. `PASSWORD_CHANGED` — `POST /api/account/change-password`

Nine event types total. `USER_DISABLED` and `USER_REACTIVATED` share one endpoint, distinguished by the resulting `is_active` value — **[RECOMMENDED]** the router branches on `payload.is_active` to choose the event type, mirroring the branch that already exists there for the self-disable/last-admin guards (`backend/app/api/routers/users.py:110`).

**Explicitly out of scope, per OD-B2 and the mandatory design facts:**

* **Login** (`POST /api/auth/login`) — **[OWNER-APPROVED]** excluded from M9.1b workflow attribution. `User.last_login_at`, updated on every successful login today, remains the sufficient record. **[INFERRED]** This is consistent, not an inconsistency: `last_login_at` already answers "when did this user last log in," which is the only question login-as-an-event would add: `audit_events` is for *actions taken on something*, and a login does not act on any `entity_type`/`entity_id`.
* **Reads** — no `GET` endpoint is attributed. **[INFERRED]** Read auditing (who viewed which patient's results) is a materially different, much higher-volume feature with different retention/performance tradeoffs; NFR-08 does not ask for it, and inventing it here would exceed the approved scope.
* **Instrument ingestion** — no artificial "system" or "instrument" user identity is created to attribute ingestion-driven `TestRun`/`Result` creation. **[OWNER-APPROVED, mandatory fact 9]** The Integration Service writes directly via SQLAlchemy outside any HTTP request and outside `get_current_user` entirely (`run_integration.py`, `app/integration/repository.py` — **[VERIFIED]**, consistent with the M9.1a design doc's own observation that "the Integration Service is a separate process ... adding API authentication cannot break instrument ingestion"). Fabricating a user for it would be exactly the kind of synthetic identity the project has previously and deliberately avoided (cf. the specimen/visit identity deferral in M8.2).
* **Failed/denied attempts (401/403)** — see §7 (OD-B3).

## **6. Event schema design**

### **6.1 Polymorphic entity reference (mandatory fact 15)**

`entity_type` (`'TEST_RUN'` | `'USER'`) + `entity_id` (integer) identify the audited object. **[OWNER-APPROVED, mandatory fact 15]** `entity_id` is deliberately **not** a foreign key — a single `audit_events` table records actions against two unrelated entity kinds (`test_runs.id_run`, `users.id_user`), and a single FK column cannot reference two different parent tables. This is the same category of tradeoff the project has already accepted elsewhere for a good reason, not a novel risk: `instrument_messages` and other traceability paths in `04_DATABASE_DESIGN.md` §16 already document non-FK identifiers where a single column must span more than one source. **[RECOMMENDED]** Application code, not the database, is responsible for `entity_id` referring to a real row — acceptable because every event is written in the same transaction as the mutation that produced it (§8), so the referenced row provably exists at insert time; it simply is not defended against being deleted afterward, which no code path in this schema currently does to a `TestRun` or a `User` (there is no delete endpoint for either — only `is_active` deactivation for `User`, and `TestRun`s are never deleted).

### **6.2 Event type**

`event_type VARCHAR` holding one of the nine values in §5. **[RECOMMENDED]** No `CHECK` constraint, validated in the application (an `AuditEventType` enum), following the schema's existing zero-CHECK-constraint convention already used for `delivery_status`, `connection_status`, and `users.role` (`docs/04_DATABASE_DESIGN.md` §8.2 pattern — **[VERIFIED]** as the established norm; **[INFERRED]** that the same norm should extend here for consistency, not because OD-B4 requires it — OD-B4 is about immutability enforcement, a separate question, see §9).

### **6.3 Actor identity (OD-B5, mandatory fact 10)**

**[OWNER-APPROVED — OD-B5 / mandatory fact 10]**

* `id_user` — `INTEGER NOT NULL`, foreign key to `users.id_user`. The **authoritative** identity. Every recorded event has a real, currently-or-formerly-active authenticated user, because every attributed endpoint requires authentication (deny-by-default, M9.1a) — there is no "system" actor to accommodate, so `NOT NULL` is safe and correct, not a design compromise.
* `actor_username` — `VARCHAR(50) NOT NULL`, a snapshot of `users.username` **at the time of the event**.
* `actor_role` — `VARCHAR(20) NOT NULL`, a snapshot of `users.role` **at the time of the event**.

**[INFERRED]** The snapshots exist because `id_user` alone is not self-contained: `users.username` could theoretically be reused after an account is disabled and a new one created with different intent (nothing in the current schema prevents reissuing a username once the original row's uniqueness constraint is no longer live for it — though today there is no delete/rename path, so this is a forward-looking protection, not a response to an observed gap), and `users.role` can change over an account's lifetime (there is no role-change endpoint yet, but nothing prevents one being added later). Reading an audit row six months after a role change should still show what role the actor *held at the time*, not their current role. The FK (`id_user`) stays the join key for "show me this row's live account"; the snapshot columns are what make the row legible on its own if that account's current state has since diverged.

### **6.4 State transition (mandatory fact 16)**

**[OWNER-APPROVED, mandatory fact 16]** `state_before` and `state_after` columns capture the relevant field(s) immediately before and after the mutation.

**[RECOMMENDED]** Small JSON objects, e.g.:

| Event | `state_before` | `state_after` |
| --- | --- | --- |
| `TEST_RUN_FINALIZED` | `{"is_final": false}` | `{"is_final": true}` |
| `TEST_RUN_UNFINALIZED` | `{"is_final": true}` | `{"is_final": false}` |
| `DELIVERY_STARTED` | `{"delivery_status": "pending"}` *or* `{"delivery_status": "failed"}` | `{"delivery_status": "sending"}` |
| `DELIVERY_DELIVERED` | `{"delivery_status": "sending"}` | `{"delivery_status": "delivered"}` |
| `DELIVERY_FAILED` | `{"delivery_status": "sending"}` | `{"delivery_status": "failed"}` |
| `USER_CREATED` | `null` | `{"username": "...", "role": "...", "is_active": true}` |
| `USER_DISABLED` | `{"is_active": true}` | `{"is_active": false}` |
| `USER_REACTIVATED` | `{"is_active": false}` | `{"is_active": true}` |
| `PASSWORD_CHANGED` | `null` | `null` |

**[RECOMMENDED, security-relevant]** `PASSWORD_CHANGED` must **never** place `password_hash` — or the plaintext new/old password — into `state_before`/`state_after`. The event exists to record *that* a change happened and *who* made it, not the credential material itself. This is worth stating explicitly in the eventual implementation's docstring, because it is exactly the kind of field a naive "snapshot the whole row" implementation would leak.

**[RECOMMENDED, new type family]** `JSONB` is proposed for both columns (`sqlalchemy.dialects.postgresql.JSONB`) as the idiomatic PostgreSQL type for a small structured snapshot. **This would be the first JSON/JSONB column anywhere in this schema** — flagged explicitly because it is a new type family, not because anything about it is unsafe; the alternative (a `TEXT` column holding a JSON-formatted string, validated only in the application) is a defensible fallback if the owner or implementer prefers to keep the schema free of PostgreSQL-specific JSON operators. This choice is **not** an OD-B decision — the owner decisions above do not specify a concrete column type — so it remains open for the implementer to confirm or revise without reopening §4–§11.

### **6.5 Timestamp**

**[RECOMMENDED]** `created_at TIMESTAMP NOT NULL, server_default = CURRENT_TIMESTAMP`, matching every other `created_at` column in the schema (`visits`, `test_runs`, `users` — **[VERIFIED]** consistent pattern).

**[RECOMMENDED]**

| Column | Type | Constraint |
| --- | --- | --- |
| `id_event` | `SERIAL` | PK, autoincrement |
| `event_type` | `VARCHAR(30)` | `NOT NULL` |
| `entity_type` | `VARCHAR(20)` | `NOT NULL` |
| `entity_id` | `INTEGER` | `NOT NULL` — not a FK (§6.1) |
| `id_user` | `INTEGER` | `NOT NULL`, FK → `users.id_user` |

| `created_at` | `TIMESTAMP` | `NOT NULL`, `server_default = CURRENT_TIMESTAMP` |

## **7. Success vs. failure recording (OD-B3, mandatory fact 14)**

**[OWNER-APPROVED — OD-B3 / mandatory fact 14]** Only successful, committed state transitions are recorded. A `401` (unauthenticated) or `403` (wrong role) response produces **no** `audit_events` row. A request that reaches a handler but is rejected by business logic — e.g. `finalize` on a run when another is already final, `409 Conflict` — **[INFERRED]** also produces no row, because no state transition occurred; there is nothing to record a before/after for. This keeps `audit_events` a record of *what happened to the system*, not a security/access log, which is a deliberately separate and explicitly out-of-scope concern (§16).

## **8. Transactional semantics**

### **8.1 Same-transaction insert (mandatory fact 3)**

**[OWNER-APPROVED, mandatory fact 3]** The audit insert occurs in the **same transaction** as the business mutation it records — i.e., inside the same `Session`, before the same `session.commit()` that persists the state change, not a separate commit before or after it.

**[INFERRED]** This is the only choice consistent with an audit trail's own purpose: if the audit write and the business write could succeed or fail independently, the log could show an action that never happened (audit committed, business rolled back) or hide one that did (business committed, audit failed) — either defeats NFR-08. Every one of the five `TestRunService` methods already has exactly one `session.commit()` (`backend/app/services/test_run_service.py` — **[VERIFIED]**), so this is additive: add the `AuditEvent` row to the session before the existing commit call, not a new commit.

### **8.2 `sync-simrs` — two audit rows, no HTTP call inside the transaction (mandatory facts 4–5)**

**[OWNER-APPROVED, mandatory facts 4 and 5]** `sync-simrs` produces exactly two `audit_events` rows: one `DELIVERY_STARTED`, and one `DELIVERY_DELIVERED` or `DELIVERY_FAILED` depending on the outbound call's outcome. The outbound HTTP call to SIMRS must **not** be wrapped in the same database transaction as either audit row.

**[INFERRED — this falls out of the existing implementation without requiring new branching logic]** `sync_simrs` (`backend/app/api/routers/test_runs.py:57-101` — **[VERIFIED]**) already calls `TestRunService.start_delivery(db, run_id)` in Phase 1 (which commits), then `SimrsClient.send(payload)` with no open transaction in Phase 2, then `TestRunService.mark_delivery_delivered` or `mark_delivery_failed` in Phase 3 (a second commit). If the audit insert is added **inside** `start_delivery`, `mark_delivery_delivered`, and `mark_delivery_failed` themselves (§13), then:

* a **direct** call to `POST /test-runs/{id}/delivery/start` produces one `DELIVERY_STARTED` row, in `start_delivery`'s own commit;
* a **direct** call to `.../delivery/success` or `.../delivery/fail` produces one `DELIVERY_DELIVERED`/`DELIVERY_FAILED` row;
* a call to `sync-simrs` produces **both**, automatically — one from its Phase 1 call to `start_delivery`, one from its Phase 3 call to `mark_delivery_delivered`/`mark_delivery_failed` — with the HTTP call sitting, exactly as it already does today, in the gap between the two commits.

No special-casing of `sync-simrs` is needed in the audit design itself; it inherits the property for free from threading the actor through the shared service methods (§13) rather than duplicating audit-insert logic in the router.

## **9. Immutability (OD-B4, mandatory fact 11)**

**[OWNER-APPROVED — OD-B4 / mandatory fact 11]** Application-level, INSERT-only discipline: no API endpoint exposes `UPDATE` or `DELETE` on `audit_events`, and the ORM model is written/used as insert-only. **No** database trigger, `REVOKE`, row-level security policy, or other DB-enforced immutability is added in this milestone.

**[INFERRED]** This mirrors the schema's existing posture on Clinical Data immutability (`04_DATABASE_DESIGN.md` §11, §25): `results` is immutable by *application convention* (no endpoint modifies `nilai_hasil`), not by a database-level write-protection mechanism, and that has been the accepted standard throughout this project (`TC-SEC-02`/`TC-API-03` in `06_QA_TEST_PLAN.md` verify it architecturally, by absence of an endpoint, not by a trigger). OD-B4 extends the same standard to `audit_events` rather than introducing a new, stronger enforcement class solely for this one table. **[RECOMMENDED]** A code-review-time reminder (a comment on the `AuditEvent` model, matching the tone already used on `Result`) that no mutating endpoint for this table should ever be added, is sufficient discipline at this milestone's scope — consistent with how `results` is protected today.

## **10. Retention (OD-B6, mandatory fact 12)**

**[OWNER-APPROVED — OD-B6 / mandatory fact 12]** Indefinite retention. No expiry, archival, or deletion policy is invented by M9.1b. **[INFERRED]** This is consistent with the table's own immutability (§9): a table designed to never be written to except by INSERT should not simultaneously need a designed-in deletion path. If retention limits are ever required (e.g. by a future hospital data-retention policy), that is a distinct, separately-scoped decision — not one this milestone should pre-empt by guessing at a duration.

## **11. Correlation / request ID (OD-B7, mandatory fact 13)**

**[OWNER-APPROVED — OD-B7 / mandatory fact 13]** No correlation ID or request ID column. **[INFERRED]** This keeps `audit_events` self-contained on the columns already justified by NFR-08 (who, what, when, before/after) without anticipating a distributed-tracing or multi-service-correlation need this single-process, single-database on-prem deployment does not currently have (`03_SYSTEM_DESIGN.md` §13 deployment architecture — one server, one process pair). If a future need arises, it can be added as a nullable column without breaking existing rows, exactly as `last_login_at` was added nullable in M9.1a.

## **12. Actor propagation mechanism (mandatory fact 2)**

**[OWNER-APPROVED, mandatory fact 2]** An explicit `actor: User` parameter, threaded from the router to the service method. **No** contextvar, thread-local, or request-global "current user."

**[VERIFIED]** This is not a new decision invented by M9.1b — it is the exact rule M9.1a's own design doc already committed to in §13, specifically so M9.1b would not have to choose between a clean design and a large refactor: *"Do not introduce a contextvar, thread-local or request-global 'current user' in M9.1a — implicit ambient identity is hard to test and makes the attribution path invisible at the call site. An explicit parameter is the design that does not paint M9.1b into a corner."* M9.1b now exercises exactly that door.

## **13. Implementation boundary — what M9.1b is expected to do**

This document is a design freeze, not an implementation. The following is **[RECOMMENDED]** as the concrete shape implementation is expected to take, restated from the task brief for completeness and cross-checked against the actual files above:

1. **One hand-authored Alembic migration**, `down_revision = "27e00bcff992"` (the current head — **[VERIFIED]**). **[INFERRED]** Hand-authored for the same reason `27e00bcff992` itself was: the ORM still carries two known, deliberately unresolved drifts against the migration chain (F-2 — `patients.nomor_rm` not yet `UNIQUE`; F-3 — four M8.4 indexes exist in the chain but in no ORM model). `alembic revision --autogenerate` at this head would still propose adding the unapproved F-2 constraint and dropping the four M8.4 indexes, exactly as it would have for the `users` migration — this risk has not gone away between M9.1a and M9.1b. The new migration must add `audit_events` alone.
2. **`AuditEvent` ORM model** (`app/models/audit_event.py`), registered in `app/models/__init__.py`, following the same conventions as `User` (§6.6, `from __future__ import annotations`, `Mapped[...]`, no `Identity`, SERIAL PK).
3. **Indexes for entity history and actor history** — **[RECOMMENDED]** `idx_audit_events_entity` on `(entity_type, entity_id)` (answers "show me everything that happened to this TestRun / this User") and `idx_audit_events_actor` on `(id_user)` (answers "show me everything this person did"), following the project's existing `idx_<table>_<purpose>` naming convention (`04_DATABASE_DESIGN.md` §20).
4. **Thread `actor: User` through the five `TestRunService` methods** (`finalize_run`, `unfinalize_run`, `start_delivery`, `mark_delivery_delivered`, `mark_delivery_failed`), each gaining the audit insert immediately before its existing `session.commit()`.
5. **Pass `current_user` from the clinical mutation routes** (`backend/app/api/routers/test_runs.py`) — each of the six route functions (five direct + `sync-simrs`, which calls the service methods internally) needs to actually declare `current_user: User = Depends(get_current_user)` and pass it through; today only the `dependencies=[_clinical_write]` list resolves the role check without capturing the `User` object into a usable parameter.
6. **Add audit rows before existing commits** — no new transactions, no new commit points; the insert joins the transaction that is already there (§8.1).
7. **Handle `sync-simrs` as two transactional audit events** — no special-case code required, per §8.2; it falls out of step 4 and 5 automatically.
8. **Add user-management audit events inline in the existing routers** (`app/api/routers/users.py` for `USER_CREATED`/`USER_DISABLED`/`USER_REACTIVATED`, `app/api/routers/account.py` for `PASSWORD_CHANGED`). **[INFERRED]** `update_user_status` already has `current_user` available (§2); `create_user` will need it added.
9. **Update test fixtures that currently use fake `id_user=0`** (`backend/tests/api/test_test_runs_api.py:79-99`, `backend/tests/test_order_overview.py:57-74`) — **[VERIFIED, concrete blocker to fix, not a design blocker]** once `audit_events.id_user` is a real FK to `users.id_user`, any test that exercises an attributed endpoint through these stub actors will violate the FK unless the fixtures create (or point to) a genuine `users` row. This does not block *design* — it is routine fixture maintenance — but it is real work the implementer must do, and is called out so it is not discovered mid-implementation.
10. **Extend migration-chain measured counts** (`backend/tests/test_migration_chain.py`) — **[INFERRED, following the established discipline]** exactly as `27e00bcff992` required measuring (not estimating) the exact table/constraint/index/not-null-column deltas on a throwaway scratch database before updating `_FINAL_TABLES`, `_FINAL_SEQUENCES`, and the count assertions, the audit-events migration must do the same. This is not optional per the project's own established norm (`docs/04_DATABASE_DESIGN.md` §29.1: *"The replacement numbers must be derived from the actual migration output, never estimated"* — carried over verbatim as a project-wide discipline, not an M9.1a-specific one).
11. **Complete audit-attribution test coverage**, at minimum: each of the nine event types is recorded with correct `entity_type`/`entity_id`/`id_user`/snapshots/state; a denied (401/403) attempt produces no row; `sync-simrs` produces exactly two rows in the right order; the actor cannot be spoofed by any client-supplied field (only `get_current_user`'s resolved identity is ever used — directly discharging the `07_TASK_LIST.md` M9.1b bullet *"tests asserting attribution is recorded and is not spoofable by the caller"*); `PASSWORD_CHANGED` never stores hash/password material in `state_before`/`state_after`.
12. **Update system/database/QA/task documentation after implementation** — mirroring the M9.1a precedent (`docs/07_TASK_LIST.md`, `docs/03_SYSTEM_DESIGN.md`, `docs/04_DATABASE_DESIGN.md`, `docs/06_QA_TEST_PLAN.md` were all reconciled once M9.1a's implementation landed). **Not done by this document** — this document is the design freeze that precedes implementation, not the post-implementation reconciliation.

None of items 1–12 is performed by this document. This document only records the frozen design they must follow.

## **14. Interaction with a future Gateway / reconciliation**

**[OWNER-APPROVED, per the task's explicit constraint]** Any future Gateway or SIMRS-reconciliation component must remain **architecture-neutral** with respect to this design — `audit_events` must not be built in a way that assumes such a component is push-based or pull-based, or that presumes its existence at all. **[INFERRED]** Nothing in §4–§13 makes that assumption: `audit_events` is populated entirely from within the existing FastAPI request/response cycle and the existing `TestRunService` transaction boundaries, with no outbound notification, no message queue, and no polling mechanism implied. A future Gateway, whichever shape it takes, would read this table the same way any other consumer would — through ordinary SQL — without M9.1b having pre-committed to how that Gateway is built.
