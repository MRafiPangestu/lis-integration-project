## 1. Objective

M9.0 addresses the database provisioning and migration reliability gap identified as F-1 in the project-wide audits.

The investigation has two goals:

1. establish the actual failure mode of the current Alembic chain when applied to a truly empty database; and
2. determine whether the historical legacy schema can be established from authoritative evidence without inventing or reconstructing unsupported history.

The investigation also records additional schema-consistency defects discovered while validating the migration chain.

## 5. Fresh-Database Experiment

### 5.1 Scratch database

A unique disposable scratch database was created:

```text
zz_m90_scratch_20260910
```

The project `.env` points to `lis_marina_permata_dev` by default, so the `DB_NAME` override was explicitly verified before invoking Alembic.

### 5.2 Empty-database result

Command executed against the empty scratch database:

```text
DB_NAME=zz_m90_scratch_20260910 py -m alembic upgrade head
```

Result:

```text
FAILED — exit code 1
```

First revision reached:

```text
b1f9dbe772fa — M1_initial_schema
```

Failing statement:

```text
CREATE TABLE visits (... FOREIGN KEY(id_pasien) REFERENCES patients (id_pasien) ...)
```

Exact failure:

```text
psycopg2.errors.UndefinedTable:
relation "patients" does not exist
```

### 5.3 Post-failure state

The scratch database contained:

```text
0 tables
```

PostgreSQL transactional DDL rolled back the failed revision, including `alembic_version`.

Therefore the failure is atomic rather than a partially applied schema.

### 5.4 F-1 verdict

**F-1 is empirically confirmed.**

The current migration chain cannot provision a truly empty database.

The correct description is:

> The migration chain is incomplete because its historical base schema is missing from the version-controlled migration graph.

It is more precise than saying that the migration chain itself is fundamentally broken.

## 6. Legacy Schema Provenance

### 6.1 Stable PoC database as historical evidence

The stable database:

```text
lis_marina_permata
```

was inspected read-only.

Observed characteristics:

- exactly the nine tables that no migration creates;
- no `visits` table;
- no `test_runs` table;
- no `alembic_version`;
- legacy constraints referenced by name by `b1f9dbe772fa` are present.

This establishes that the database is a genuine pre-M1 legacy installation rather than an ordinary current development database.

### 6.2 Corroborating evidence

The `downgrade()` body of `b1f9dbe772fa` reconstructs the legacy columns removed by M1, including:

- legacy `orders` columns;
- legacy `results` columns;
- legacy `instrument_messages` nullability assumptions.

Every constraint that the M1 migration drops by name was found in the legacy database schema.

### 6.3 Empirical replay

A schema-only dump of `lis_marina_permata` was restored into the disposable scratch database.

The full existing migration chain was then executed:

```text
legacy schema
    ↓
b1f9dbe772fa
    ↓
4a24240f8c32
    ↓
621889e316b5
    ↓
c5465739f048
    ↓
4aff9e134f16
```

Result:

```text
EXIT CODE 0
```

The chain succeeded completely.

### 6.4 Provenance conclusion

The legacy schema is now established from authoritative live evidence.

The investigation therefore rejects the need to fabricate a pre-M1 schema from the final ORM or from incomplete documentation.

Important limitation:

> The authoritative legacy schema exists as a live database artifact and is not yet version-controlled. It must be preserved before any migration remediation is implemented.

## 7. Schema Consistency Verification

The following sources were compared:

1. `04_DATABASE_DESIGN.md`
2. SQLAlchemy `Base.metadata`
3. schema produced by the legacy dump + current migration chain
4. `lis_marina_permata_dev` (read-only)

### 7.1 Overall result

- 11 tables expected.
- 11 tables produced by the chain.
- 11 tables in ORM.
- 11 tables in the development database.
- 0 table-set mismatches.
- 0 column-set mismatches.

### 7.2 F-2 — missing `patients.nomor_rm` UNIQUE in migration chain

The following all expect the constraint:

```text
04_DATABASE_DESIGN.md
SQLAlchemy ORM
lis_marina_permata
lis_marina_permata_dev
```

But the current migration chain does not create it.

Therefore a clean database provisioned only through the migration chain would not reproduce the required `patients.nomor_rm` uniqueness.

**Verdict: MAJOR — reproducibility and patient-identity integrity defect.**

This must be discharged by M9.0.

### 7.3 F-3 — ORM / M8.4 index drift

The four M8.4 query indexes exist in the migration chain and database, but are not declared in ORM metadata.

Consequently:

```text
alembic check
```

proposes dropping those indexes.

A future `alembic revision --autogenerate` could therefore produce destructive `DROP INDEX` operations.

**Verdict: MAJOR — migration/ORM drift defect.**

The preferred fix is ORM declaration of the existing indexes if no schema change is required.

## 8. Remediation Options

### Option A — Hand-authored historical baseline

Create a new first migration by manually reconstructing the legacy schema from documentation and the M1 downgrade logic.

**Rejected.**

Reason:

- the final database design describes the final state, not the legacy state;
- `b1f9dbe772fa.down_revision` only gives a delta-inverse for objects it touches;
- missing historical details would have to be invented.

This violates the requirement to avoid fabricated migration history.

### Option A′ — Evidence-derived historical baseline

Create a new first revision mechanically from a schema-only capture of the actual legacy database.

Conceptually:

```text
lis_marina_permata
       ↓
pg_dump --schema-only
       ↓
version-controlled evidence artifact
       ↓
R0
       ↓
b1f9dbe772fa
       ↓
...
       ↓
head
```

The exact R0 generation mechanism is a Phase 2 implementation decision, but it must be mechanically traceable to the preserved legacy schema artifact.

**Recommended.**

Advantages:

- preserves actual historical structure;
- avoids fabrication;
- retains the existing M1 transformation logic;
- makes fresh installation reproducible;
- was empirically validated during this investigation.

### Option B — Final-schema squashed baseline

Replace the historical chain with a new final-schema baseline.

**Not preferred.**

It would simplify fresh installs but discard valuable migration history and make the proven legacy transformation path harder to preserve.

### Option C — Idempotent baseline

Use an `IF NOT EXISTS` style bootstrap so the baseline silently does nothing when the schema already exists.

**Rejected.**

Silent acceptance of a partially correct database is unsafe for a clinical system and weakens migration correctness.

### Option D — External bootstrap SQL only

Require operators to run an external SQL file before Alembic.

**Rejected as the primary remedy.**

This would leave `alembic upgrade head` unable to provision an empty database and would preserve the core F-1 defect.

## 9. Recommended M9.0 Design

### 9.1 Overall direction

**Option A′ — evidence-derived historical baseline**, plus F-2 and F-3 reconciliation.

The implementation should be separated into these logical steps:

```text
Phase 1 — Investigation
    ↓
capture and preserve authoritative legacy schema
    ↓
freeze provenance
    ↓
review exact artifact
    ↓
Phase 2 — Implementation
    ↓
create R0 from preserved artifact
    ↓
fix F-2
    ↓
reconcile F-3 at ORM level
    ↓
fresh-install verification
    ↓
CI migration smoke test
```

### 9.2 R0

R0 should:

- have `down_revision = None`;
- reproduce the actual pre-M1 legacy schema;
- be mechanically generated from the preserved schema artifact;
- record source database, capture date, capture method, and provenance;
- never contain clinical data or `INSERT` statements.

`b1f9dbe772fa` should then become a child of R0.

### 9.3 F-2

The chain must produce:

```text
UNIQUE(patients.nomor_rm)
```

for a fresh database.

The exact migration mechanism should be selected during Phase 2 implementation after compatibility with already-stamped installations is considered.

### 9.4 F-3

The four M8.4 indexes already exist in the chain/database.

The preferred remediation is to declare them correctly in ORM metadata so `alembic check` no longer proposes to drop them.

No additional migration is required solely to recreate indexes that are already produced by `4aff9e134f16`, unless implementation testing proves otherwise.

## 10. Installation Classes

M9.0 must explicitly distinguish installation classes.

### 10.1 New installation

Expected path:

```text
empty PostgreSQL database
        ↓
alembic upgrade head
        ↓
final schema
```

No manual legacy SQL bootstrap should be required.

### 10.2 Existing legacy installation

For an existing database matching the proven pre-M1 schema:

```text
legacy database
      ↓
alembic stamp R0
      ↓
alembic upgrade head
```

This operation must be explicit and documented. It must never silently rewrite or migrate data.

### 10.3 Existing development database

`lis_marina_permata_dev` is already at the current Alembic head.

Once R1/F-2 and any required ORM reconciliation are implemented, the development database should be upgraded normally and verified against a fresh-install schema.

### 10.4 Stable PoC database

```text
lis_marina_permata
```

must remain untouched.

It serves as:

```text
historical evidence source
```

and not as a migration target.

No `stamp`, upgrade, downgrade, truncate, alter, or seed operation should be performed against it as part of M9.0 remediation.

## 11. Migration CI / Verification Design

A permanent migration smoke test should provision a disposable PostgreSQL database using the real Alembic chain.

Minimum concept:

```text
1. Create unique scratch DB.
2. Assert the resolved DB name is not a project database.
3. Run `alembic upgrade head`.
4. Assert exit code 0.
5. Assert expected Alembic head.
6. Assert all 11 expected tables.
7. Assert critical constraints.
8. Assert the four M8.4 indexes.
9. Compare against Base.metadata.
10. Optionally run `alembic check`.
11. Optionally test downgrade behavior in a disposable database.
12. Drop scratch DB.
```

Critical safety requirements:

- generated unique scratch database name;
- explicit DB target override;
- hard deny-list for project databases;
- guaranteed cleanup.

### ORM / migration drift control

Use:

```text
alembic check
```

against a database provisioned from the migration chain, not against a manually prepared development database.

This catches:

- ORM-declared objects missing from migrations;
- migration-declared objects missing from ORM metadata;
- destructive future autogenerate drift.

## 12. Rollback / Downgrade Safety

The new baseline is expected to contain legacy tables and columns that M1 immediately transforms.

That is historically correct, but it creates an operational hazard.

`R0.downgrade()` must not be treated as a routine production operation because it may drop the legacy schema and therefore clinical data.

The implementation must either:

- make destructive downgrade behavior explicitly fail-safe for non-empty installations; or
- document and test a strict operational rule that downgrading below M1 is allowed only on disposable/fresh databases.

The final decision belongs to M9.0 implementation design.

## 17. Investigation Conclusion

F-1 is no longer an inference. It has been empirically demonstrated:

```text
empty DB
   ↓
alembic upgrade head
   ↓
b1f9dbe772fa
   ↓
CREATE TABLE visits
   ↓
patients missing
   ↓
FAIL
```

The investigation also proved the complementary fact:

```text
actual legacy schema
      ↓
current migration chain
      ↓
head
      ↓
SUCCESS
```

Therefore the safest interpretation is:

> **The migration chain is historically valid but incomplete because its pre-M1 base schema is not represented in the version-controlled Alembic graph.**

The investigation further identified:

```text
F-2 = missing patients.nomor_rm UNIQUE in migration chain
F-3 = ORM metadata drift for four M8.4 query indexes
```

The recommended direction is:

```text
preserve legacy schema evidence
        ↓
generate evidence-derived R0
        ↓
retain b1f9dbe772fa transformation
        ↓
fix F-2
        ↓
reconcile F-3
        ↓
fresh-install migration test
        ↓
alembic check in CI
```

No migration remediation has been implemented by this investigation.
