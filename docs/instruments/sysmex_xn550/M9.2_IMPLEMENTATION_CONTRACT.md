### 0.4 The contract on one screen

1. **Transport:** listener mode for the tested port-5001 configuration (OD-XN-1 **approved**), peer allowlist, one active session per instrument, where a new connection supersedes the old one. No outbound byte other than `0x06`. **Never NAK**, and never withhold an ACK as a protocol signal.
2. **Boundaries:** messages are assembled from a per-session byte stream: a CR-terminated `H` record through a CR-terminated `L` record. A `recv()` is never a message, and a connection is never a message.
3. **Raw first:** each complete message is committed with its exact bytes, SHA-256, session, offsets and timing **before** any parsing. Fragments are preserved too.
4. **Parsing:** pure and fail-closed. Only the **observed envelope** (§6.3) is eligible for normalisation; every structural deviation is kept raw and marked `UNCLASSIFIED`, with a specific rule token.
5. **Classification and persistence:** the observed XN-550 messages **are result-bearing** (patient-result-like content). But patient and specimen identity and message-category coverage are not established, so **XN-550 messages are not promoted to the existing clinical `PATIENT_RESULT` path under this contract.** A conformant message is recorded as `UNCLASSIFIED` / `XN550_ENVELOPE_CONFORMANT`, and its normalised results go to a **new unlinked-observation layer**, never to `patients` / `visits` / `orders` / `test_runs` / `results`. Any future promotion requires a separate approved contract (§23). Terminology: §0.5.
6. **Identity:** specimen identity and patient identity are **UNRESOLVED** by design. `O`-4 component 3 is a display label, not a key. The sequence number is never used and is not transmitted anyway.
7. **Idempotency:** each delivery is always preserved raw. A **byte-identical** redelivery creates no second result set. A **same-content, different-bytes** delivery creates a new result set flagged `POSSIBLE_DUPLICATE` and is never suppressed. Nothing is keyed on reconnects, sessions or batches.
8. **No regression:** the BC-5150 parser, MLLP client, classification policies, clinical path and all existing tests stay unchanged, except the deliberate update of one guard test when the XN-550 key is registered (§19.1).

### 0.5 Terminology — three layers that must not be conflated

| Layer | Term used here | Meaning | Status under this contract |
|---|---|---|---|
| **A. Wire / message content** | **Result-bearing message** (the validation records' *patient-result message*, a corpus category label) | What the bytes contain: an `H P C O C R… C L` message carrying analysis results for a sample, captured during routine patient work | **Observed** — 20 corpus messages (E-06) |
| **B. XN-550 observation classification** | Outcome of the XN-550-specific policy `xn550_observed_envelope`, recorded as `classification_rule` | `XN550_ENVELOPE_CONFORMANT` (eligible for the unlinked-observation layer), `XN550_DEV_*` (structural deviation), or an `UNPARSEABLE` token. In `message_class` it is stored as `UNCLASSIFIED` or `UNPARSEABLE` | **Defined and required** (§6, §17) |
| **C. Existing clinical `PATIENT_RESULT` path** | `MessageClass.PATIENT_RESULT` (M8.2) | The existing gate that creates `Patient` / `Visit` / `Order` / `TestRun` / `Result` rows (used by the BC-5150 policies) | **Not used for the XN-550.** XN-550 messages are not promoted to it under this contract |

**Why a conformant message is `UNCLASSIFIED`.** In this repository `message_class` is the M8.2 **clinical-persistence gate**. `PATIENT_RESULT` means "enters the clinical hierarchy", not "the payload contains patient results". An XN-550 message can therefore be result-bearing (layer A) and envelope-conformant (layer B) while `message_class` stays `UNCLASSIFIED`, because promotion to layer C needs two things this contract does not have:
- a verified patient/specimen identity rule (§12);
- message-category coverage — QC, calibration, maintenance and startup are NOT OBSERVED, so S4 cannot be evaluated.

This is a boundary of the **current contract**, not a statement that XN-550 data can never become clinical results. A separate, approved contract may introduce promotion once evidence and identity rules exist (§23). BC-5150 classification is unaffected.

## 1. Scope and non-goals

### 1.1 In scope — what the implementation governed by this contract delivers

- A **listener transport** for the tested XN-550 configuration (TCP port 5001). OD-XN-1 is **approved**, scope in §0.3.
- A **CR-record ASTM message assembler** that is safe under fragmentation and multiple messages per session.
- **Raw-first persistence** with exact bytes and transport provenance.
- A **pure, versioned XN-550 E1394 parser** with an envelope check and structural result-record classification.
- An **unlinked-observation persistence layer**, including duplicate handling at the message and analysis level.
- **Read-only API and frontend views** for unlinked XN-550 results, gated by OD-XN-3.
- **Tests** at every layer (§20) and objective acceptance criteria (§21).

### 1.2 Non-goals — explicitly excluded

| Excluded | Why |
|---|---|
| Creating or matching `Patient`, `Visit`, `Order`, `TestRun` or `Result` rows from XN-550 data | No specimen or patient identifier is proven (§12). The `O`-4 Sample No. is operator free text that often holds a name — the **S1** hazard (`VALIDATION_2026-09-16.md` §8.3) |
| Promoting XN-550 messages to the existing clinical `PATIENT_RESULT` path (§0.5, layer C). They are result-bearing, but stay `UNCLASSIFIED` unlinked observations | Patient/specimen identity is not established (§12), and QC / calibration / maintenance / startup message shapes are **NOT OBSERVED**, so **S4** cannot be evaluated (`docs/09` §9.6, §14). Promotion needs a separate approved contract (§23) |
| Final Run selection, SIMRS delivery, patient-history inclusion | These depend on the clinical hierarchy, which is excluded |
| Business deduplication that suppresses a result whose bytes differ | Genuine rerun and cross-day resend semantics are UNVERIFIED (§13) |
| NAK, ACK withholding, ACK-timeout handling, host query/pull, send-all or queue-flush triggering, E1381 de-framing | All UNVERIFIED; no outbound protocol behaviour beyond the verified `0x06` |
| QC / calibration filtering rules | Zero captures |
| Retrieving image files referenced by `R`-4 paths | Out of scope; the paths embed PHI |
| Any change to BC-5150 behaviour | Isolation requirement (§3.2, AC-XN-22) |
| Physical testing, database contact, schema migration **in this checkpoint** | Design-only task |

### 1.3 What this checkpoint changes

This new document, and a pointer row in [`README.md`](README.md) §9. **Nothing else.**

## 4. Transport contract

### 4.1 Role and prerequisite

In the tested configuration the XN-550 dials the LIS on port 5001 (E-01), and the LIS's reverse-direction SYNs to the instrument's port 5001 were silently dropped (E-02). For this configuration the LIS **MUST** therefore listen.

- **Evidence vs. decision:** the field evidence establishes the prerequisite. Building listener mode is the separate S7 architecture decision, which the project owner has **approved** (**OD-XN-1**, §0.3).
- **Scope:** the approval covers TCP port 5001 in the tested ASTM output configuration. Inbound acceptance on other ports is **UNKNOWN**, and **no port scan is authorised**. Nothing here claims the instrument cannot behave differently under another port or output configuration.
- **If the configuration changes:** its transport role **MUST** be re-established by field evidence before this section is relied on.

### 4.2 Configuration shape (additive)

```json
{
  "key": "sysmex_xn550",
  "instrument_name": "Sysmex XN-550",
  "mode": "listener",
  "host": "<LIS lab-interface IP to bind>",
  "port": 5001,
  "allowed_peers": ["<instrument IP>"],
  "parser_key": "xn550_astm_e1394",
  "classification_policy": "xn550_observed_envelope",
  "ack_policy": "ack_per_read_on_receive",
  "ingestion_stage": "raw_only",
  "enabled": false
}
```

| Field | Rule |
|---|---|
| `mode` | `SUPPORTED_INSTRUMENT_MODES` gains `"listener"`. `"client"` behaviour is unchanged |
| `host` / `port` | In listener mode, the **bind** address and port. `0.0.0.0` **SHOULD NOT** be used in production; bind to the laboratory interface. Startup **MUST** fail if two enabled listener configs share `(host, port)` |
| `allowed_peers` | **Required and non-empty** in listener mode (a validation error otherwise). Exact IP match, no CIDR in the first implementation |
| `parser_key` | Exact registry key (§19.1). Its protocol family **MUST** match `mode`: an ASTM parser with `client` mode, or `bc5150_hl7` with `listener` mode, fails at startup |
| `classification_policy` | For the XN-550, only `xn550_observed_envelope`. Unlike the HL7 path, an unknown value for a listener/ASTM instrument **MUST** fail at startup instead of falling back |
| `ack_policy` | Required in listener mode; exact values from §4.5; unknown values fail at startup |
| `ingestion_stage` | `raw_only` or `observations` (§19.3); unknown values fail at startup |
| `identity_prefix` | Optional in listener mode. If present it **MUST NOT** be used by any XN-550 code path. It stays required for `client`/HL7 configs, so BC-5150 validation is unchanged |

The configuration never holds a numeric database id. Identity resolution by `instrument_name` is unchanged.

### 4.3 Connection acceptance and peer policy

1. When a connection is accepted and the peer IP is **not** in `allowed_peers`, the LIS closes it immediately: no read, no ACK, no session row. It logs the peer address and port at WARNING. Nothing reaches the database.
2. There is **at most one active session per instrument**. If an allowed peer connects while a session is active, the **new connection supersedes the old one**. The old socket is closed; its partial buffer becomes a fragment (§5.5); its session closes with `SUPERSEDED`. **Rationale:** after an abrupt instrument power loss, the old session can remain half-open indefinitely. Instrument connection limits are UNKNOWN. Refusing the new connection could lock the instrument out, while the observed normal-restart pattern (E-16) is a fresh SYN.
3. The listener **MUST** stay available across session closures: it keeps LISTENING while no session is active (observed with the evidence tool, 09-17 §17.3).

### 4.4 Session lifecycle

| State | Entered when | Leaves when | `connection_status` |
|---|---|---|---|
| `STOPPED` | Service not running, or instrument disabled | Worker starts | `DISCONNECTED` |
| `LISTENING` | Socket bound, no active session | Allowed peer accepted | `LISTENING` (new, §4.10) |
| `CONNECTED` | Allowed peer accepted; `instrument_sessions` row opened | Peer FIN / RST, read error, supersede, shutdown, persistence failure (§4.8) | `CONNECTED` |
| `CLOSING` | Any close trigger | Buffer finalised to a fragment if non-empty; session row closed with `close_reason` | — (transient) |
| `BIND_FAILED` | Bind or listen raised | Worker thread ends; the existing `Supervisor` restarts it after 5 s | `RECONNECTING` (existing semantics: worker being restarted) |

`close_reason` domain: `PEER_RESET`, `PEER_CLOSED`, `READ_ERROR`, `SUPERSEDED`, `LIS_SHUTDOWN`, `PERSISTENCE_FAILURE`, `RECOVERED_AT_STARTUP` (a session row still open when the service starts is closed with this reason and `closed_at` = service start time; its true end time is unknown).

### 4.5 ACK policy

**Facts (E-18).** The only behaviour ever used against this instrument is a single `0x06` per socket read, sent on receipt and before anything is stored, and it never interrupted a transmission. ACK dependence, ACK timeout and NAK reaction are UNVERIFIED. In MULTI-SELECT-01, each next message followed the instrument's TCP ACK of our `0x06` (E-15). That is consistent with, but does not prove, the instrument waiting for it.

| Policy value | Behaviour | Status | Residual risk |
|---|---|---|---|
| `ack_per_read_on_receive` | After every successful `recv()` returning ≥ 1 byte, send exactly one `0x06` **before** assembly and persistence. **Target:** within 5 ms of the read (verified tool: 0.16–1.71 ms internal) | **FIELD-VERIFIED baseline** — default | **Durability gap:** bytes are acknowledged before they are committed. A crash between read and T1 commit loses that in-flight message silently. The window is bounded by the message's remaining reads plus T1 latency (§14.3). Recovery is operator retransmission (E-13) |
| `ack_per_message_after_raw_commit` | No ACK for intermediate reads. One `0x06` after the complete message's T1 commit succeeds | **NOT FIELD-VERIFIED** — selectable only after a controlled, authorised physical validation (OD-XN-4) | Changes ACK timing and count; unknown instrument reaction |

Rules that hold under **every** policy:

- The only outbound byte ever sent is `0x06`. **`0x15` (NAK) MUST NOT exist as a code path.** No `ENQ`, `EOT`, query, command or text is ever written. `send_command` stays unimplemented.
- **An ACK is a transport receipt, not a statement of validity.** Parse failures, envelope deviations, duplicates and fragments **MUST NOT** change ACK behaviour. A NAK's or a withheld ACK's effect on this instrument is unknown and could trigger unobserved retry loops.
- ACKs are also sent for bytes that turn out to be E1381 control bytes (§5.3). This preserves the verified per-read uniformity; the bytes are kept raw.
- The session records its `ack_policy` (§9.1) so every message's acknowledgement regime is provenance.

### 4.6 Inbound byte handling

- Reads use a bounded buffer (e.g. 4 096 bytes, the size the existing client uses). A read size never has meaning.
- A read timeout (e.g. 1 s) exists **only** to check the stop event. It **MUST NOT** close the session or finalise a partial message.

### 4.7 Idle sessions and keepalive

- **The LIS MUST NOT close an idle session.** Idle sessions with zero bytes were held for 20–41 minutes (E-03). After a LIS-side close, no reconnect occurred within 5 min 16 s (E-17).
- **TCP keepalive is OFF by default.** Its effect on the instrument is NOT FIELD-VERIFIED. Recovery from a half-open session relies on supersede-on-new-connection (§4.3). **Known limitation:** after an abrupt power loss, `connection_status` may show `CONNECTED` for a dead session until the instrument reconnects.
- No application heartbeat is expected. None was observed, in contrast to the BC-5150's `0x02`.

### 4.8 Persistence failure

If the T1 commit for a completed message or fragment fails:

1. Retry the commit with bounded backoff (e.g. 3 attempts over ≤ 2 s), keeping the bytes in memory.
2. If it still fails, close the session with `PERSISTENCE_FAILURE`, stop accepting connections for this instrument until a health check (a `SELECT 1`) succeeds, and log at ERROR **without payload**: SHA-256, length and session offsets only.
3. **Known consequence, recorded:** a LIS-initiated close may leave the instrument disconnected for an unknown period (E-17). The operational runbook **MUST** require (a) confirming the instrument's session is re-established after the database recovers, and (b) manual retransmission of results whose SHA-256 appears in the ERROR log but not in `instrument_messages`.

Under `ack_per_read_on_receive` these bytes were already acknowledged, so step 3(b) is the only recovery path.

### 4.9 LIS shutdown and restart

- Shutdown closes the active session (`LIS_SHUTDOWN`), finalises any partial buffer as a fragment, then closes the listening socket, reusing the `Supervisor` shutdown path.
- **UNVERIFIED:** whether a graceful LIS-side FIN, as opposed to the observed RST, changes how quickly the instrument reconnects. Until that is validated, the runbook treats every LIS restart as potentially needing operator action to re-establish the session.
- A restart **never** implies resend and never triggers deduplication decisions (§16).

### 4.10 Status reporting

- `write_instrument_status` is reused. The values are `LISTENING` (new), `CONNECTED`, `RECONNECTING`, `DISCONNECTED`.
- `GET /api/instruments/status` adds `LISTENING` to its valid set, an additive API delta. The frontend sidebar renders it as "Listening — no instrument session".
- Status writes **MUST NOT** carry payload data.

### 4.11 Transport logging

**Allowed:** instrument key, session id, peer and local address and port, byte counts, read and ACK counts, offsets, SHA-256, rule tokens, close reason.

**Forbidden:** any payload byte, the Sample No., any `P` field value, any image path, any exception message that could echo payload text.

This extends M9.1a's "never log credentials" rule to PHI and anticipates M9.5's structured logging. The XN-550 modules **MUST** use `logging`, never `print`.

## 5. ASTM message-boundary contract

### 5.1 Invariants

- **I-1:** One `recv()` is **not** one message (E-04).
- **I-2:** One TCP connection is **not** one message (E-03, E-15).
- **I-3:** A message is exactly the bytes from the first byte of an `H` record through the `CR` that terminates the next `L` record in the same session stream.
- **I-4:** Assembly state is **per session**. A new session starts with an empty buffer; bytes never carry across sessions.
- **I-5:** Every received byte ends up in exactly one of: a complete message, a fragment (§5.5), or an out-of-message segment (§5.2). **No byte is silently discarded.** This differs from MLLP, where pre-frame heartbeat noise is dropped, because no XN-550 heartbeat or noise has been observed and any unexpected byte is S11 evidence.

### 5.2 Assembler state machine

The assembler consumes bytes, splits records at `CR` (`0x0D`) and keeps an unterminated tail for the next read. Record recognition uses only the first two bytes of a record (`<type>|`).

| State | Input (a complete CR-terminated record) | Action | Next state |
|---|---|---|---|
| `IDLE` | Record starting `H\|` | Start a message at this record's first byte | `IN_MESSAGE` |
| `IDLE` | Any other record | Append to the **out-of-message segment** | `IDLE` |
| `IN_MESSAGE` | Record starting `L\|` | Append; emit `CompleteMessage` | `IDLE` |
| `IN_MESSAGE` | Record starting `H\|` | Emit the current bytes as `Fragment(reason=TRUNCATED_BY_NEW_HEADER)`; start a new message here | `IN_MESSAGE` |
| `IN_MESSAGE` | Any other record | Append | `IN_MESSAGE` |
| any | Session close | Emit a non-empty buffer or unterminated tail as `Fragment(reason=INCOMPLETE_AT_CLOSE)` | — |

When a `H|` record arrives in `IDLE` and the out-of-message segment is non-empty, that segment is emitted first as `Fragment(reason=BYTES_OUTSIDE_MESSAGE)`. It is also emitted at session close.

The assembler recognises boundaries only. It does **not** validate record order, field counts or `L`-3 content; the parser does (§6), so a malformed but bounded message is still one raw row.

### 5.3 Byte-class checks (fail closed, raw preserved)

| Condition | Assembler result | Rule token |
|---|---|---|
| Any of `0x02` STX, `0x03` ETX, `0x04` EOT, `0x05` ENQ, `0x06` ACK, `0x15` NAK, `0x17` ETB, or any other byte `< 0x20` except `CR` | Boundaries are still found by §5.2; the containing message or fragment is marked `UNPARSEABLE` | `XN550_E1381_OR_CONTROL_BYTE` |
| `LF` (`0x0A`) anywhere | As above | `XN550_UNEXPECTED_LF` |
| Any byte `≥ 0x80` | As above; encoding unverified | `XN550_NON_ASCII_BYTE` |

Each detection raises one WARNING per session (not per byte), because it is new vendor behaviour (S11).

### 5.4 Completion

A message is complete **only** when the `CR` terminating an `L|` record has been read. Silence alone never completes a message.

After **30 s** without new bytes while in `IN_MESSAGE`, emit one WARNING with the session id and buffered length. This does **not** finalise or discard the buffer, because inventing a timeout semantics could split a slow but legitimate message. The largest observed intra-message delays are milliseconds (E-15).

### 5.5 Fragments

A fragment is persisted through T1 exactly like a message (§9), with:

- `parse_status = Failed`
- `message_class = UNPARSEABLE`
- `classification_rule` set to one of `XN550_FRAGMENT_INCOMPLETE_AT_CLOSE`, `XN550_FRAGMENT_TRUNCATED_BY_NEW_HEADER`, `XN550_FRAGMENT_BYTES_OUTSIDE_MESSAGE` or `XN550_FRAGMENT_SIZE_LIMIT`

A fragment is **never** parsed into observations, and never takes part in duplicate detection.

### 5.6 Size limits (resource guards, not semantics)

| Limit | Value | Basis |
|---|---|---|
| Maximum message or fragment bytes | 65 536 | About 20× the observed maximum (3 133 B) |
| Maximum records per message | 512 | About 10× the observed maximum (55) |
| Maximum out-of-message segment | 65 536 | Same guard |

When a limit is reached, the buffered bytes are emitted as a fragment (`XN550_FRAGMENT_SIZE_LIMIT`), the assembler returns to `IDLE`, and scanning resumes at the next `H|` record. These are code constants with named tests, not configuration.

### 5.7 Offsets and timing captured for each message or fragment

- `stream_offset_start` (inclusive) and `stream_offset_end` (exclusive), counted from byte 0 of the session. These are the same convention as the evidence offsets (09-17 §3).
- `first_byte_at`: the LIS clock at the read containing the first byte.
- `received_at`: the LIS clock at the read containing the last byte.
- `read_count`: the number of reads contributing bytes.
- `session_message_index`: 1-based ordinal of messages and fragments in the session.

All are naive server-local timestamps, consistent with the existing schema convention.

### 5.8 Future E1381 framing

If an output setting ever produces E1381 framing, it **MUST** be added as a separate de-framing layer **below** this assembler. That layer would verify frame numbers and checksums, and emit the de-framed record stream to this assembler unchanged. Until evidence exists, §5.3 keeps such bytes raw and unparsed. The assembler **MUST NOT** strip or tolerate control bytes speculatively.

## 6. Record parsing contract

### 6.1 Stages

```text
raw bytes ─► (1) decode ─► (2) records ─► (3) tokenise ─► (4) envelope check ─► (5) field map ─► (6) R-shape ─► (7) normalise
             ASCII strict   split on CR    | \ ^ &          §6.4 table          §7               §6.5          §10
```

Each stage either passes on its output or returns a **failure token**, never both. Stages 1–3 failing give `UNPARSEABLE`. Stage 4–6 failures give `UNCLASSIFIED` with a deviation token. Only a message that passes all stages is normalised, and its classification is also `UNCLASSIFIED`, with rule `XN550_ENVELOPE_CONFORMANT`. The positive XN-550 outcome is carried by the rule token (layer B). It is not a promotion to the clinical `PATIENT_RESULT` path (layer C, §0.5).

### 6.2 Decode, record split and tokenisation

1. **Decode:** strict ASCII. §5.3 already rejects non-ASCII and control bytes, so failure here is a defensive `UNPARSEABLE / XN550_DECODE_ERROR`.
2. **Records:** split on `CR`. The element after the final `CR` **MUST** be empty (observed 23/23), otherwise `UNPARSEABLE / XN550_TRAILING_BYTES`. An empty record between two `CR`s gives `UNPARSEABLE / XN550_EMPTY_RECORD`. A record's type is its first character, and the second character **MUST** be `|`.
3. **Delimiters:** `H`-2 **MUST** be exactly `\^&` (field `|` is implied by position). Any other declaration gives `UNPARSEABLE / XN550_UNEXPECTED_DELIMITERS`. The parser uses the declared delimiters, which currently equal the constants.
4. **Tokenisation order:** record → fields (`|`) → repeats (`\`) → components (`^`). **Escape decoding happens last, per component.** The only sequences recognised are E1394's `&F&` → `|`, `&S&` → `^`, `&R&` → `\`, `&E&` → `&`. Any other `&…&` sequence in a normalised field gives `UNCLASSIFIED / XN550_DEV_UNKNOWN_ESCAPE`. Only `&R&` has been observed, inside image paths.
5. **The raw text of every field is retained in the parse result.** Decoded values are derived and never replace raw text in provenance.

### 6.3 The observed envelope

A message is **envelope-conformant** only if all of these hold. Every condition was satisfied by all 22 patient-result files and is justified in §2.2:

```text
H P C O C R{1..} C L              exactly one H (first), P, O, L (last); C after P, after O, after last R
fields: H 13 · P 26 · O 26 · C 4 · R 13 · L 3
```

### 6.6 Purity and versioning

- The parser is a pure function of `bytes`. It **MUST NOT** import the database, sockets, settings or the clock. Its import graph is checked by AC-XN-12.
- It exposes a constant `PARSER_VERSION`, e.g. `"xn550-astm-1.0.0"`. Every change to envelope checks, shape rules, field mapping or normalisation bumps the version, and T2 stores it on each message row it classifies (§9.2, §19.5).
- **Output is deterministic:** the same bytes and version always give the same result, including the analysis fingerprint (§13.4).
- Stored observations are never re-derived automatically after a version change. Re-evaluation is an explicit, separately designed operation (§23).

## 8. Field semantic confidence levels

### 8.1 Definitions

| Level | Meaning | What the implementation may do |
|---|---|---|
| **VERIFIED SEMANTICS** | Meaning established by pre-registered ground truth, or unambiguous structure confirmed across the corpus | Normalise and display with the verified meaning |
| **STRONGLY OBSERVED BUT SEMANTICS PARTIAL** | Constant or systematic across the corpus; the meaning is only standard-consistent or plausible | Use as a structural eligibility condition, or display verbatim with a neutral label. **Never** base identity or clinical decisions on it |
| **RAW-ONLY / UNKNOWN SEMANTICS** | Varies without explanation, or has no attested meaning | Keep in raw bytes. Optionally store presence booleans. **No** normalised value, API field or display (image-path, `P`-5 and `P`-8 values especially). **Exception, pinned in revision 6 (CI-1):** the result-content values in §7.5 — `R`-3 component 6, interpretive scores and the `A` / `W` flags — are **stored** verbatim in `instrument_result_items` (§10.3), so each observation record is complete. `R`-3 component 6 is never exposed (Appendix B.4); whether scores and `A` / `W` are **shown** is decision OD-XN-3.2 |
| **NOT OBSERVED** | Empty or absent in every capture | Keep raw. A populated value is new evidence (§18) |

### 8.3 Promotion rule

A field moves **up** a level only through a documented field observation that meets `docs/09` §12. Changing a level is a contract change, which bumps `PARSER_VERSION` if the parser's behaviour changes. **S12 applies:** no rule from a single observation. A field moves **down** immediately when contradicting evidence appears (S10).

## 9. Raw message persistence contract

**Principle:** every complete message and every fragment is committed durably, with exact bytes and transport provenance, in its **own transaction (T1)** before any parsing. A T1 row is never deleted. Its raw columns are never updated after insert. Only the status columns set by T2/T3 change — `parse_status`, `error_detail`, `message_class`, `classification_rule`, `parser_key`, `parser_version` and `duplicate_of_message_id` — and only while the row is `Pending`. A row that has left `Pending` is never updated again (§13.2).

| `CHECK (raw_bytes IS NULL OR raw_length = octet_length(raw_bytes))` | Integrity | Cheap guard |
| `CHECK (raw_bytes IS NULL OR raw_sha256 IS NOT NULL)` | Integrity | Raw without hash is not allowed |
| Index `(id_instrument, raw_sha256)` | **Non-unique** | Byte-identity lookup. **Must not be unique:** same-day retransmissions are byte-identical and each delivery is a fact to keep (E-13, 09-16 §10.1) |
| Index `(id_instrument, received_at DESC)` | Non-unique | Operations and list queries |
| Index `(duplicate_of_message_id)` | Non-unique | Delivery lists |

### 9.3 T1 procedure

1. Insert the session row at accept, and commit.
2. For each `CompleteMessage` / `Fragment`: insert the message row with the raw columns, `parse_status = 'Pending'` (fragments: `Failed` + token at insert), then commit.
3. Only after the commit may T2 start for that message. Under `ack_per_message_after_raw_commit`, only after the commit may the `0x06` be sent.
4. Commit failure follows §4.8.

### 10.4 T2 procedure (same transaction for all observation rows)

This is the G2 T2 stage. It serves both `ingestion_stage` values and replaces the Phase 2 stage (§19.5). The Phase 2 stage implements steps 1–3 and 5 only, without step 0 or step 4.

0. **Serialise** (MUST from G2; §14.2). Begin the transaction and take the per-instrument advisory lock. Then re-read the message row `FOR UPDATE`. If it is no longer `Pending`, roll back and stop (no-op).
1. Verify `raw_sha256` and `raw_length` against `raw_bytes`. On a mismatch → `Failed` / `UNPARSEABLE` / `XN550_RAW_INTEGRITY_MISMATCH`; commit; stop. Otherwise parse `raw_bytes` (§6). `Unparseable` → `Failed` / `UNPARSEABLE` + token; commit; stop.
2. Envelope deviation → `Success` / `UNCLASSIFIED` + token; commit; stop.
3. Conformant → the classification is `UNCLASSIFIED` / `XN550_ENVELOPE_CONFORMANT`. The message is result-bearing and eligible for the unlinked-observation layer, and it is **not** promoted to the clinical `PATIENT_RESULT` path (§0.5).
4. **Byte-identity root link** (§13.2), in **both** stages. If other delivery-group members exist, set `duplicate_of_message_id` to the lowest `id_message` among them and `error_detail = 'Redelivery: byte-identical to message <id>'`.
5. If `ingestion_stage = raw_only` → `Success`; commit; stop (no set).
5a. If any delivery-group member already owns a result set → `Success`; commit; **no new set**; stop.
6. Compute fingerprint v1 (§13.4). Look up the lowest `id_result_set` with the same `(id_instrument, fingerprint_version, analysis_fingerprint)`, and set `duplicate_status` and `possible_duplicate_of` from the result.
7. `IdentityResolver` returns `UNRESOLVED` (§12.4).
8. Insert the set and all its items; set the message to `Success`; **single commit**.
9. Any exception, including a lock timeout → **T3:** roll back T2 entirely, so no link, set or item survives. Then record `Failed` / `UNPARSEABLE` / `XN550_T2_EXCEPTION` on the row, and only while it is still `Pending`:
   - `error_detail` holds the token only;
   - the log receives the exception **type name** only — never the exception message or traceback, which could echo payload text (§4.11, AC-XN-26).

Every outcome of steps 1–8 also writes `parser_key` and `parser_version`. Each commit or rollback ends the transaction and releases the lock.

Observation rows are **immutable**: no UPDATE or DELETE code path exists, following the `docs/03` §7.2 clinical-immutability principle.

### 10.5 What is deliberately not persisted in normalised form

`P`-5 / `P`-8 values · `P`-9 · `H`-5 · `O`-4 padding and components 1, 2, 4 · `O`-5 · `O`-12 / `O`-26 (implied by conformance) · `R`-11 · image-path values · interpretive-score semantics. All remain recoverable from `raw_bytes` with `parser_version`.

### 11.1 Byte offsets and text layers (pinned, revision 6)

Five layers are kept apart. Only the first three are bytes.

1. **Session stream.** Every byte read on one TCP session.
   - *Storage:* not stored as one value; it is rebuilt from the session's messages and fragments (PV-3).
   - *Position:* `instrument_messages.stream_offset_start` / `stream_offset_end` — session-relative, `[start, end)`. A message includes its final CR (§5.7).
2. **Message wire bytes.** The exact bytes of one message.
   - *Storage:* `instrument_messages.raw_bytes` — **authoritative**.
   - *Position:* offset 0 is the message's first byte (the `H`).
3. **Record wire bytes.** One `R` record, without its CR.
   - *Storage:* `raw_bytes[source_offset_start:source_offset_end]`.
   - *Position:* message-relative `[start, end)`. `source_offset_start` is the offset of the record's `R`; `source_offset_end` is the offset of its terminating CR.
4. **Wire field text.** The record bytes read as ASCII and split on the field delimiter, then on the component delimiter (§6.2).
   - *Storage:* not stored.
   - *Position:* no field-relative offsets are stored. A field is located by its record's offsets plus its field number, which `parser_version` fixes (mapping above).
5. **Semantic text.** Wire field text after E1394 escape decoding (`&F&`, `&S&`, `&R&`, `&E&` → the field, component, repeat and escape delimiter characters). For `sample_label` only, leading and trailing ASCII spaces are also removed.
   - *Storage:* the normalised columns `test_code`, `test_code_qualifier`, `value_raw`, `units_raw`, `reference_range_raw`, `abnormal_flag_raw`, `result_status_raw` and `sample_label`.

**Rules:**
- **Semantic text is not wire bytes.** The contract never treats it as wire bytes and never assumes the two are equal. They differ whenever a component contains an escape sequence, and, for `sample_label`, whenever padding was removed.
- **What §2.2 observed is not a guarantee.** In the frozen corpus, escape sequences occurred only inside image-path values, which are never normalised. That is an observation about that corpus.
- **Derived positions are computed, not stored.** A record's session position is `stream_offset_start + source_offset_start`; a field's position comes from splitting the record bytes.
- **Tracing an item back:** `id_item` → its set → `id_message` → `raw_bytes[source_offset_start:source_offset_end]` → the field number → escape decoding → the stored semantic text (PV-2).

**Provenance guarantees:**
- **PV-1:** `sha256(raw_bytes) == raw_sha256` and `len(raw_bytes) == raw_length` for every XN-550 row.
- **PV-2:** Re-running the parser version named in `parser_version` over `raw_bytes` reproduces every parse-derived value:
  - on each item: `source_record_index`, `source_offset_start`, `source_offset_end`, `source_r_sequence`, `item_kind`, `test_code`, `test_code_qualifier`, `value_raw`, `units_raw`, `reference_range_raw`, `abnormal_flag_raw` and `result_status_raw`;
  - on the set: `analysis_at`, `sample_label`, `p5_populated`, `p8_populated`, `item_count`, `non_n_flag_item_count`, `image_reference_count` and `analysis_fingerprint`.
- **PV-3:** Concatenating a session's messages and fragments in `stream_offset_start` order reproduces the session's received byte stream, with no gaps or overlaps (I-5).
- **PV-4:** Each delivery group (§13.2) owns at most one result set. The §14.2 lock guarantees this; no constraint does.
  - The set points to exactly one member message, and every member is found by the §13.2 membership predicate.
  - `duplicate_of_message_id`, **when set**, points to the group's lowest-`id_message` member. Rows classified before the G2 T2 stage keep NULL and are never backfilled.
  - Delivery counts never depend on the pointer.
- **PV-5:** Provenance columns are never exposed in full to the frontend (Appendix B). Investigators read them through controlled database access.
- **PV-6:** For every item, `0 ≤ source_offset_start < source_offset_end < raw_length`, the byte at `source_offset_end` is CR (`0x0D`), and the record begins with the two bytes `R|`.

## 12. Identity / specimen association strategy

### 12.1 Five identities, kept separate

| | Identity | What identifies it | Proven? | Stored as |
|---|---|---|---|---|
| **A** | **Instrument message** (one delivered application message) | `instrument_messages.id_message`, locatable as `(id_session, stream_offset_start)` | Technical, by construction | PK + unique `(session, offset)` |
| **B** | **Specimen** (the physical sample) | **Nothing in the message.** `O`-3 empty; no barcode; sequence not transmitted and resets on restart; `O`-4 is operator free text | **No** (E-09) | Not stored. `association_status = UNRESOLVED` |
| **C** | **Patient** | **Nothing verified.** `P`-5 intermittent / UNKNOWN; no name in `P`; `O`-4 may contain a name but is not a patient key | **No** | Not stored. No `patients` row |
| **D** | **Transmission** (a delivery event) | The `instrument_messages` row itself: session, offsets, `first_byte_at` / `received_at`. The instrument sends no transmission id (`H`-3 empty) | Technical | The message row. Byte-identical deliveries form a delivery group computed by the §13.2 predicate; `duplicate_of_message_id`, when set, points to the group's lowest-id member |
| **E** | **Result** | Within a set: `(id_result_set, test_code)`. Across deliveries of the same analysis: **no proven identity** — only the `analysis_fingerprint` grouping hint (§13.4) | Technical within a set; **not** across sets | Item PK + set-level fingerprint |

### 12.2 Direct answers

| Question | Answer |
|---|---|
| **Technical message identifier** | `instrument_messages.id_message`. Its natural technical key is `(id_session, stream_offset_start)`. `raw_sha256` identifies **byte content**, not a message: two deliveries can share it |

## 13. Idempotency / duplicate handling strategy

**Ordering rule (pinned, revision 6).** In this contract, *earliest* and *earlier* mean the **lowest primary-key id**: the lowest `id_message` for deliveries, and the lowest `id_result_set` for result sets. The rule applies everywhere: this section, §10, §11, Appendices A–C and the acceptance criteria.
- **Why ids:** ids come from each table's sequence (default cache of 1), so they follow insertion order. Under the §14.2 lock, that is also processing order.
- **Clocks are never used** to order a duplicate decision — not `received_at`, `first_byte_at` or `analysis_at`. Clock values can tie, and clocks can move.

### 13.1 Four duplicate classes

| Class | Definition | Detectable from | Evidence status | Strategy |
|---|---|---|---|---|
| **Transport duplicate** | The same TCP bytes delivered twice at the transport layer | TCP sequence numbers (kernel) | By construction of TCP | **Nothing to do** within a session. Bytes of a message cut off by a session end become a **fragment** (never parsed); a later complete resend is a normal message. Fragments never take part in duplicate detection |
| **Message duplicate** | A complete message **byte-identical** to an earlier successful message from the same instrument | `(id_instrument, raw_sha256)` | Same-day manual retransmission is byte-identical — VERIFIED, one controlled pair (E-13); 09-16 message A ×4, cause UNVERIFIED | Keep the delivery row; **no second result set** (§13.2) |
| **Business duplicate** | A different-bytes message carrying the same analysis result | `analysis_fingerprint` | **UNVERIFIED.** The only candidate (09-16 A vs 09-17 Seq 58) is a hypothesis | **Flag only**, never suppress (§13.3) |
| **Genuine new clinical result** | A new analysis (e.g. a rerun of the same specimen) | Expected, not verified: a different `R`-13 and/or values | Genuine rerun **UNVERIFIED** | New result set, `duplicate_status = NONE`. No rerun linkage |

### 13.2 Message duplicate (byte identity)

This section applies to **envelope-conformant** messages only. Fragments, unparseable messages and deviations have no result sets, so no duplicate decision is needed for them.

- **Delivery group — exact membership predicate.** There is no time window, and the Phase 1 index `(id_instrument, raw_sha256)` serves the lookup:

  ```sql
  id_instrument = :id_instrument AND raw_sha256 = :raw_sha256
  AND framing = 'ASTM_CR_RECORDS' AND parse_status = 'Success'
  AND classification_rule = 'XN550_ENVELOPE_CONFORMANT'
  ```

  The group is always computed by this query. It is what the API reports as deliveries (Appendix B), and it is never reconstructed by following `duplicate_of_message_id`.
- **Root link** (G2 T2 stage, both stages, §10.4 step 4). When a delivery is classified conformant and other group members already exist, it gets:
  - `duplicate_of_message_id` = the lowest `id_message` among them — never a chain;
  - `error_detail = 'Redelivery: byte-identical to message <id>'`.

  The lowest-id member itself keeps NULL.
- **Rows classified before the G2 T2 stage.** The Phase 2 stage makes no link, so those conformant rows keep `duplicate_of_message_id = NULL` and `error_detail = NULL`.
  - **No backfill and no retroactive UPDATE.** Status columns change only while a row is `Pending` (§9), and §10.6 allows no data migration.
  - **They remain full group members.** They count in `delivery_count`, appear in `deliveries[]`, and can be the lowest-id member that later deliveries point to.
  - Rows still `Pending` when the G2 stage is deployed are processed by it and linked normally.
- **Set rule.** A result set is created only if no group member already owns one (§10.4 step 5a). That decision is taken under the §14.2 lock. The set belongs to the first delivery processed in stage `observations`. So:
  - bytes first seen under `raw_only` still get their set when redelivered after switching to `observations`;
  - a delivery whose T2 failed (not `Success`) is not a group member and never blocks a later identical delivery.
- **Membership ignores `parser_version`.** A later parser version that classifies identical bytes differently leaves the new row outside the group; this fails closed.
- **Safety argument (technical inference, not instrument semantics):** a byte-identical message repeats the same `R`-13 to the second, the same Sample No., every value and flag, and the same image-path folder date. Nothing is lost by not creating a second set: every delivery row stays and is listed.

### 13.3 Business duplicate (possible duplicate)

- **Lookup:** the lowest `id_result_set` with the same `(id_instrument, fingerprint_version, analysis_fingerprint)`, taken under the §14.2 lock. Index `idx_instrument_result_sets_fingerprint` serves it.
- **If found:** the new set is created with `duplicate_status = 'POSSIBLE_DUPLICATE'` and `possible_duplicate_of` = that id. This never forms a chain, because the lowest-id set for a fingerprint is always `NONE`.
- **Invariants:**
  - The database enforces that status and pointer agree and that the pointer targets a lower id (`ck_instrument_result_sets_duplicate_state`, §10.2).
  - The G2 DB tests assert that the target has the same instrument, fingerprint version and fingerprint, and `duplicate_status = 'NONE'`.
- **Never:** suppress, merge, hide, or pick a "winner". Both sets are fully visible, with a badge.
- **Why no suppression:** it is unverified whether equal content across different bytes always means the same analysis (§22). A wrong suppression would hide a real result, a silent clinical data loss. A wrong flag is visible and harmless.

### 13.4 Analysis fingerprint (version 1)

**Semantic inputs — unchanged since revision 1:**
- the instrument;
- `R`-13;
- the Sample No. label;
- for every item, in `R`-2 order: `R`-2, test code, qualifier, item kind, value, units, reference range, flag and status.

Revision 6 pins only the byte encoding. No fingerprint has been computed or stored before this revision, because G2 is not implemented.

```text
analysis_fingerprint = lowercase hex of SHA-256(FP1)            -- 64 characters

FP1 = encode(field 1) + encode(field 2) + ...  (byte concatenation, in exactly this order)

   1  "xn550-analysis-fingerprint"    literal domain tag
   2  1                               fingerprint_version
   3  id_instrument
   4  analysis_at_raw                 R-13: the 14 digits of the wire field
   5  sample_label                    stored semantic text (§10.2)
   then, for each item in ascending source_r_sequence:
   6  source_r_sequence
   7  test_code
   8  test_code_qualifier             or NULL
   9  item_kind
  10  value_raw                       or NULL (always NULL for FLAG_ONLY and IMAGE_REFERENCE)
  11  units_raw                       or NULL
  12  reference_range_raw             or NULL
  13  abnormal_flag_raw               or NULL
  14  result_status_raw

encode(NULL)    = the single byte "-" (0x2D)
encode(text)    = the ASCII decimal byte length of text, then ":" (0x3A), then text as US-ASCII bytes
encode(integer) = encode(its decimal digits, with no sign and no leading zeros)
```

- **Unambiguous by construction.** Every field is self-delimiting and every item has exactly nine fields, so different inputs always give different FP1 bytes. No JSON, key ordering, whitespace or number-formatting convention is involved.
- **Text fields are the stored semantic text** (§11.1). They are US-ASCII by construction, because §5.3 rejects bytes ≥ `0x80` before parsing. A non-ASCII character is a T2 exception (§10.4 step 9); it is never replaced or skipped.
- **NULL versus empty string.** An empty string would encode as `0:` and NULL as `-`. Optional columns store NULL, never an empty string (§10.3).
- **Included:** only fields whose change would mean different clinical content.
- **Excluded:**
  - image-path values — the folder date varies by day (E-14) and the file name embeds the label;
  - `H`;
  - all `P` fields — `P`-5 population varies without explanation (E-20);
  - `O`-5, `O`-12 and `O`-26 — constant for conformant messages;
  - `R`-11.
- **Evidence check (by construction):** 09-16 message A and 09-17 Seq 58 differ only in 4 bytes inside image-path values (E-14). Those values are excluded, so the two produce the **same** fingerprint. They would be flagged `POSSIBLE_DUPLICATE`, not merged, which matches the hypothesis status exactly.
- **Not a key.** The fingerprint is not unique and not exposed via the API. Changing its inputs or its encoding requires a new `fingerprint_version`; older sets are never recomputed in place.

| Scenario | Raw rows | Result sets | Flags |
|---|---|---|---|
| Exact same message delivered again (any time) | +1 | +0 once a group member owns a set | `duplicate_of_message_id` → the lowest-id group member |

## 14. Multi-message TCP session behaviour

### 14.1 Requirements

- **MS-1:** Every message in a session is independent: its own T1 row, its own T2 transaction, its own outcome. A failing message (deviation, T2 exception) **MUST NOT** affect earlier or later messages in the same session.
- **MS-2:** Messages are persisted in **arrival order**, with `session_message_index` and offsets recording that order. No batch or grouping entity exists.
- **MS-3:** Several complete messages delivered in **one read** are emitted and persisted in order (E-04 coalescing).
- **MS-4:** A message spanning several reads is persisted once, with `read_count` > 1.
- **MS-5:** The session stays open after each message. Completing a message never closes a connection.

### 14.2 Processing model

- One **reader** per active session and one **ordered processing path** per instrument.
- **T1 MUST run inline** in the reader path as soon as a message or fragment completes. That keeps the unpersisted window minimal, especially under `ack_per_read_on_receive`.
- **T2 MAY run inline.** If measured `T1 + T2` p95 exceeds **100 ms** at corpus message sizes on target hardware, T2 **MUST** move to a single ordered per-instrument worker that consumes committed `Pending` message ids. Because T1 has committed, a crash leaves `Pending` rows. They are re-processed in id order at startup, idempotently: only rows still `Pending` are processed, and a row that owns a set or carries a link is never `Pending`, because both are written in the commit that ends `Pending`.
- **Concurrency — per-instrument serialisation, MUST from G2** (revision 6; previously SHOULD):
  - **When.** Every T2 transaction that makes a cross-row decision MUST take a transaction-scoped PostgreSQL advisory lock for its instrument first. The cross-row decisions are the §13.2 root link, the §10.4 step 5a set-ownership check and the §13.3 fingerprint lookup — that is, the G2 stage in both `raw_only` and `observations`. The Phase 2 stage makes no cross-row decision and takes no lock.
  - **The lock.** `SELECT pg_advisory_xact_lock(1479882032, :id_instrument)`. The first key is the fixed XN-550 T2 namespace: ASCII `X550` read as a 32-bit integer (`0x58353530`). No other advisory lock exists in this repository.
  - **Wait.** The wait is bounded by `SET LOCAL lock_timeout = '30s'`, set immediately before the lock is taken. A timeout is a T2 exception (§10.4 step 9).
  - **Scope.** The lock covers the whole T2 transaction, and commit or rollback releases it:
    - re-reading the message row `FOR UPDATE` and stopping unless it is `Pending`;
    - integrity verification and parsing — a pure, in-process step over at most 65 536 bytes;
    - classification;
    - the byte-identity lookup and root link;
    - the set-ownership check;
    - the fingerprint lookup;
    - the set and item inserts;
    - the message update;
    - the commit.
  - **Never inside the lock:** socket reads or writes to the instrument, ACKs, T1 raw inserts, session-row or status writes, HTTP or SIMRS calls, sleeps or retry backoff. T1 never takes the lock, so raw capture is never blocked by T2.
  - **Why MUST.** A session thread that outlives its 5 s join (`HANDLER_JOIN_TIMEOUT_SECONDS`), on supersede or on worker shutdown, can run T2 at the same time as a new session thread or a restarted worker's `process_pending` (§19.6.3, DUP-2). The lock is what guarantees at most one result set per delivery group (PV-4); no database constraint can express that.
  - **Latency.** If waiting for the lock pushes inline T2 past the 100 ms budget above, T2 moves to the per-instrument worker (existing rule).

### 14.3 The unpersisted window under `ack_per_read_on_receive`

Bytes are at risk only between their read and the T1 commit of the message containing them. That is the time for the remaining reads of that message (observed milliseconds) plus one small INSERT. The window is documented. It is not eliminated without OD-XN-4.

## 15. Multi-select batch behaviour

- **MSB-1:** A multi-select transmit is treated as **nothing more than several messages arriving in one session** (E-15). The ingestion layer **MUST NOT** detect, name, group or count "batches". No schema entity, column or API field represents a batch.
- **MSB-2:** Five messages within ~0.6 s **MUST** produce five raw rows and, when conformant and not byte duplicates, five result sets, in arrival order (AC-XN-19).
- **MSB-3:** No inference from batch arrival: arrival order is **not** interpreted (what determines it is UNKNOWN, 09-17 §19.5); the absence of unselected records is **not** generalised; a burst is **not** evidence of send-all or queue flush.
- **MSB-4:** Throughput headroom. The design target is ≥ 20 conformant messages per second per instrument, without message loss and without ACK latency beyond the §4.5 target, measured with the loopback harness (§20). The observed maximum is 5 in 543.3 ms.
- **MSB-5:** Repeating a multi-select is covered by §13.5.

## 16. Restart / reconnect behaviour

Evidence E-16 and E-17 defines **transport resilience requirements only**.

| ID | Requirement |
|---|---|
| RR-1 | The listener survives any session end and returns to `LISTENING` without restarting the worker (§4.3–§4.4) |
| RR-2 | A new connection from an allowed peer is always accepted, superseding a stale session (§4.3) |
| RR-3 | **Reconnect ≠ resend.** No component may expect, wait for, request or infer retransmission after a new session |
| RR-4 | **No payload ≠ no pending queue.** No component may record, display or infer "nothing pending" from a quiet session (09-17 §17.5, §9.3) |
| RR-5 | **No deduplication from reconnect.** Session boundaries never enter duplicate logic (§13.5) |
| RR-6 | Session rows record every reconnect (`opened_at`, peer port, `close_reason`), so reconnect behaviour stays observable in production without extra tooling |
| RR-7 | An instrument-side `RST` (normal shutdown, E-16) is a normal close (`PEER_RESET`), logged at INFO — not an error |
| RR-8 | No reconnect timer is assumed. The LIS **never** closes a session to "encourage" reconnection |
| RR-9 | An open session row found at service start is closed as `RECOVERED_AT_STARTUP` (§4.4); its buffered bytes were in memory and are lost, and the runbook recovery in §4.8 applies |
| RR-10 | The instrument's startup background check is **not** expected to reach the LIS (E-22). If a startup-time message ever arrives, it goes through the normal envelope check with no special casing |

## 17. Error and malformed-message behaviour

**Two rules hold in every row below:**
- **ACK behaviour never changes** (§4.5).
- **No row creates clinical data.**

**Why structural deviations are `Success` / `UNCLASSIFIED` and not `Failed`:** the bytes *were* parsed. What failed is eligibility, and keeping that distinction lets operations tell "garbage on the wire" apart from "a well-formed message of an unobserved kind" (for example, a possible QC message). This follows the existing M8.2 separation of `parse_status` from classification.

**Why conformant rows are also `UNCLASSIFIED`:** `message_class` is the clinical-persistence gate (§0.5). A conformant row is distinguished by `classification_rule = XN550_ENVELOPE_CONFORMANT`, and it feeds only the unlinked-observation layer. No row in the table above is promoted to the clinical `PATIENT_RESULT` path under this contract.

**`error_detail` format:** it never contains field text, and takes exactly one of two forms:
- `<TOKEN>[ @record <index>[ field <n>]]`, matching `^[A-Z0-9_]+( @record \d+( field \d+)?)?$`;
- the redelivery note `Redelivery: byte-identical to message <id_message>`, matching `^Redelivery: byte-identical to message \d+$`.

**XN-550 message-row states (pinned, revision 6).** The code and tests enforce these as an application domain. `instrument_messages` is shared with BC-5150, whose rows use other values, so G2 adds no CHECK to that table.

| State | `parse_status` | `message_class` | `classification_rule` | `error_detail` | Result set |
|---|---|---|---|---|---|
| Awaiting T2 | `Pending` | NULL | NULL | NULL | Never |
| Fragment or byte-class failure (T1) | `Failed` | `UNPARSEABLE` | `XN550_FRAGMENT_*`, `XN550_E1381_OR_CONTROL_BYTE`, `XN550_UNEXPECTED_LF` or `XN550_NON_ASCII_BYTE` | The token | Never |
| Unparseable (T2) | `Failed` | `UNPARSEABLE` | An unparseable token from the table above; a §5.3 byte-class token only defensively | Token form | Never |
| Integrity mismatch (T2) | `Failed` | `UNPARSEABLE` | `XN550_RAW_INTEGRITY_MISMATCH` | The token | Never |
| T2 exception (T3) | `Failed` | `UNPARSEABLE` | `XN550_T2_EXCEPTION` | The token | Never |
| Envelope deviation | `Success` | `UNCLASSIFIED` | `XN550_DEV_*` | Token form | Never |
| Conformant | `Success` | `UNCLASSIFIED` | `XN550_ENVELOPE_CONFORMANT` | NULL, or the redelivery note | Only as §13.2 allows, and only in stage `observations` |

- `message_class` is never `PATIENT_RESULT` or `NON_PATIENT` for an XN-550 row.
- `parser_key` and `parser_version` are NULL only on rows that T2 has not processed: `Pending` rows and T1 failures.
- `duplicate_of_message_id` is non-NULL only on conformant rows classified by the G2 stage.

**Observability:** a periodic count by `classification_rule` (a log metric or SQL view) **SHOULD** exist, so that any `XN550_DEV_*`, `XN550_E1381_*` or `XN550_FRAGMENT_*` occurrence is visible. **Each is new field evidence** and triggers the `docs/09` §14 S11 review.

| **Structural** (grammar, record set, counts, constant codes in §6.4) | New record type, populated `O`-3, `R`-9 ≠ `F`, `O`-12 ≠ `N` | Envelope deviation: raw kept, `UNCLASSIFIED`, no observations, S11 review |
| **Value in a normalised field** (within the known structure) | New test code; new flag letter; new unit; non-decimal measured value; populated `R`-6 | **Stored verbatim**; set still created; one WARNING per message, `XN550_NOVELTY_<FIELD>` with record index (no value). Display is verbatim — unknown flags render as unknown (Appendix C) |
| **Value in a raw-only field** | Different `P`-5 length; `P`-9 value outside `U`/`M`/`F`; different `O`-4 component 4; different `H`-5 | Raw only. At most a presence boolean. INFO novelty counter without value |
| **Empty-in-corpus field becomes populated** (`R`-8, `R`-10, `R`-12, `P`-3/`P`-4/`P`-7…) | — | Raw only; `XN550_NOVELTY_POPULATED_FIELD` WARNING (field number only). It is not normalised until promoted per §8.3 |

### 18.2 Rules

- **U-1:** Allow-list normalisation. Only the fields in §11's mapping are ever normalised; every other byte stays in `raw_bytes`.
- **U-2:** No semantic mapping of codes: no flag translation, no unit conversion, no test-code renaming, no reference-range lookup.
- **U-3:** Verbatim storage never implies a meaning. The API and UI show verbatim codes with neutral labels (Appendix B/C).
- **U-4:** Novelty warnings never contain values, only field numbers, record indices and tokens.
- **U-5:** No automatic filtering of "non-essential" parameters (`docs/03` FR-03). Every `MEASURED`, `INTERPRETIVE` and `FLAG_ONLY` item is kept; image paths are the only exclusion (PHI plus non-result). Clinical parameter selection belongs to a future association phase with master-data mapping (§23). This includes `WBC-D`, `WDF-X`/`-Y`/`-Z` (unit `ch`), `MICROR`, `MACROR`: these codes' clinical role is **not interpreted**.

## 19. Parser registry / feature gating

### 19.1 Registry

- **Key:** `xn550_astm_e1394`, exact match, no aliases, no case folding.
- **Registration shape:** the registry gains an explicit **protocol family** per key (`HL7_MLLP`, `ASTM_E1394_CR`). The recommended shape is a static `ParserBinding(key, family, parse, version)`, with `resolve_parser("bc5150_hl7")` kept **byte-for-byte compatible** for HL7 callers. A new `resolve_binding(key)` is used by `run_integration` for dispatch. An unknown key still raises `ParserNotRegisteredError` with no fallback.
- **Startup validation** (fail loudly, before any worker or status write):
  - the key is registered;
  - the family matches `mode` (`HL7_MLLP` ↔ `client`, `ASTM_E1394_CR` ↔ `listener`);
  - `classification_policy`, `ack_policy` and `ingestion_stage` are valid for the family (§4.2);
  - listener `(host, port)` pairs are unique.
- **Guard-test update — deliberate and reviewed:** `tests/test_xn550_astm_contract.py::test_no_astm_parser_is_registered_in_production` asserted `KNOWN_PARSER_KEYS == {"bc5150_hl7"}` until the key was registered. The implementation commit that registers the key **MUST** replace it with an exact-set assertion `{"bc5150_hl7", "xn550_astm_e1394"}`, and keep asserting that `xn550_astm`, `sysmex_xn550` and `astm_generic` raise. Phase 2 did exactly this, as `test_only_the_dedicated_xn550_astm_parser_is_registered` (§19.5). The rest of that module stays unchanged as the evidence contract.
- **XN-550 policy:** `xn550_observed_envelope` lives with the XN-550 parser, is typed on `AstmParseResult`, and returns `Classification`. **Under this contract it does not return `PATIENT_RESULT`.**
  - Envelope-conformant, result-bearing messages get `UNCLASSIFIED` / `XN550_ENVELOPE_CONFORMANT` and are routed only to the unlinked-observation layer.
  - Returning `PATIENT_RESULT` would promote XN-550 messages into the existing clinical path (`Patient` / `Visit` / `Order` / `TestRun` / `Result`), which requires a separate approved contract (§0.5, §23).
  - The HL7 policy registry, `resolve_policy`'s strict fallback and every BC-5150 policy are unchanged.

## Appendix A — Backend contract (conceptual interfaces)

These interfaces are illustrative and non-normative in naming. The behaviour they carry is normative, via the referenced sections.

```text
# --- transport (§4) --------------------------------------------------------
class ListenerTransport:                      # one per enabled listener instrument; Supervisor-managed
    def __init__(self, runtime: RuntimeInstrument, session_handler_factory, status_writer): ...
    def serve_forever(self) -> None           # bind, accept, peer allowlist, supersede
    def stop(self) -> None                    # Supervisor contract: idempotent, never blocks shutdown

class AckPolicy(Protocol):                    # §4.5 — exact config values only
    name: str
    def after_read(self, n_bytes: int) -> int        # number of 0x06 bytes to send now (0 or 1)
    def after_raw_commit(self) -> int                # 0 or 1
# There is no method, constant or branch capable of emitting 0x15.

class SessionHandler:                         # one per accepted connection
    def run(self) -> CloseReason              # read loop → AckPolicy → assembler → RawMessageStore → T2 dispatch

# --- boundaries (§5) ---------------------------------------------------------
class AstmRecordAssembler:                    # pure, per session, no I/O
    def feed(self, chunk: bytes, read_at: datetime) -> list[AssemblerEvent]
    def close(self, closed_at: datetime) -> list[AssemblerEvent]
AssemblerEvent = CompleteMessage(raw: bytes, offset_start, offset_end, first_byte_at, last_byte_at,
                                 read_count, byte_class_token | None)
               | Fragment(raw: bytes, offset_start, offset_end, first_byte_at, last_byte_at,
                          read_count, reason_token)

# --- parsing & classification (§6, §7) --------------------------------------
PARSER_VERSION: str
def parse_xn550_astm(raw: bytes) -> AstmParseResult            # pure
def classify_xn550(result: AstmParseResult) -> Classification   # UNCLASSIFIED | UNPARSEABLE + rule token;
                                                                # not promoted to PATIENT_RESULT under this contract (§0.5)
def normalize_xn550(parsed: Parsed) -> NormalizedResultSet      # only for XN550_ENVELOPE_CONFORMANT
def analysis_fingerprint_v1(id_instrument: int, normalized: NormalizedResultSet) -> str   # §13.4 FP1 encoding; lowercase hex SHA-256

# --- persistence (§9, §10) ---------------------------------------------------
class SessionStore:
    def open(self, ctx: SessionContext) -> int                   # id_session (own commit)
    def close(self, id_session: int, reason: CloseReason, counters: SessionCounters) -> None
    def close_orphans_at_startup(self, id_instrument: int) -> int  # RECOVERED_AT_STARTUP

class RawMessageStore:                                           # T1
    def persist(self, id_instrument: int, id_session: int, index: int,
                event: AssemblerEvent) -> int                    # id_message; own commit; §4.8 on failure

class DuplicateDetector:                                          # §13; called only under the §14.2 lock
    def byte_identical_root(self, id_instrument: int, raw_sha256: str) -> int | None        # lowest id_message in the §13.2 group
    def group_owns_result_set(self, id_instrument: int, raw_sha256: str) -> bool             # §10.4 step 5a
    def earliest_same_fingerprint(self, id_instrument: int, fingerprint_version: int,
                                  fingerprint: str) -> int | None                            # lowest id_result_set

class IdentityResolver:                                           # §12.4
    def resolve(self, normalized: NormalizedResultSet) -> IdentityResolution   # UNRESOLVED

class ObservationStore:                                           # T2 (single transaction)
    def persist_result_set(self, id_message: int, normalized: NormalizedResultSet,
                           duplicate: DuplicateOutcome, identity: IdentityResolution) -> int

def process_astm_message(id_message: int, *, stage: IngestionStage, session_factory,
                         parser, policy, detector, resolver, store) -> None   # T2 + T3 orchestration;
                                                                              # §10.4 step 0 takes the §14.2 lock first

# --- error reporting (§4.11, §17) -------------------------------------------
class IngestionErrorReporter:
    def transport_event(self, session_id: int | None, token: str, **counters) -> None
    def message_outcome(self, id_message: int, token: str, record_index: int | None = None,
                        field_no: int | None = None) -> None      # never accepts payload text
```

**Dependencies:** transport → assembler → stores. The parser, policy, normaliser and fingerprint import nothing from database or transport. `run_integration.worker_factory` dispatches by registry family (§19.1) and hands a `ListenerTransport` to the existing `Supervisor` as the worker's `client`.

### B.1 Principles, authentication and authorisation

- **Routes:** exactly two, both **GET** — `GET /api/instrument-results` (B.2) and `GET /api/instrument-results/{id_result_set}` (B.3).
  - They live in a new router, `app/api/routers/instrument_results.py`, with `prefix="/instrument-results"`, included in `api_router`.
  - They therefore inherit `Depends(get_current_user)` from the `/api` mount (M9.1a, deny-by-default).
  - `PUBLIC_ROUTES`, CORS and the auth router do not change.
- **Authentication:** the Bearer JWT, as today. A missing, malformed or expired token, or an inactive user, gets the existing generic 401.
- **Authorisation:** set by the OD-XN-3.1 answer.
  - *Proposed default, pending that answer:* any authenticated role (ANALYST or ADMIN), as for existing clinical reads.
  - *If OD-XN-3.1 restricts visibility:* both routes add `require_role(...)` with the recorded roles, and other roles get 403.
  - As today, the role is read from the live user row, never from the token.
- **Read-only:**
  - no POST, PUT, PATCH or DELETE on XN-550 observations;
  - no link, finalise, unfinalise, deliver, retransmit, SIMRS sync, query or re-evaluate action;
  - reads write no `audit_events` rows (M9.1b scope).
- **Isolation:**
  - Existing endpoints are unchanged and never include XN-550 observations: `/api/results`, `/api/patients/{nomor_rm}/history`, `/api/instruments/{id}/orders`, `/api/orders/{id}/test-runs` and the workflow POSTs.

- **No clinical joins:**
  - The service reads only `instrument_result_sets`, `instrument_result_items`, `instrument_messages`, `instrument_sessions` and `instruments`.
  - It never reads, joins or imports `patients`, `visits`, `orders`, `test_runs`, `results`, `users` or `audit_events`.
- **Status codes:** 200 · 401 · 403 (only under a restricting OD-XN-3.1 answer) · 404 (unknown `id_result_set`) · 422 (invalid parameters).

- message-processing columns: `duplicate_of_message_id`, `parse_status`, `message_class`, `classification_rule`, `error_detail`, `framing`;
- transport detail: `stream_offset_start`, `stream_offset_end`, `first_byte_at`, `session_message_index`, the session counters and `close_reason`;
- every deviation, fragment or unparseable message.

### B.5 Schemas and modules

- **Pydantic models** live in `app/schemas/instrument_results.py`: `PaginatedInstrumentResultSetResponse`, `InstrumentResultSetSummary`, `InstrumentResultSetDetail`, `InstrumentResultItemResponse`, `InstrumentResultDeliveryResponse` and `InstrumentResultProvenanceResponse`.
  - Each derives directly from `pydantic.BaseModel`.
  - No existing schema class is imported, extended or modified.
- **TypeScript types** mirror them exactly — same names, same fields — in `frontend/src/types/api.ts`. No interface extends a clinical type (`ResultResponse`, `OrderOverviewRow`, `PatientResponse` or any other).
- **Field types:** datetimes serialise like existing naive datetimes (no offset). Status-like fields are plain strings, following the existing convention; the database enforces their domains (§10.2, §10.3).
- **Service** in `app/services/instrument_result_service.py`.
- **Import guard:** the router, schema and service modules, and the observation store, import no clinical model and no clinical schema. An import-graph test enforces this (AC-XN-14).

### B.6 Explicitly prohibited

- Search or filter by Sample No. (`sample_label`). This is the pinned default that OD-XN-3.4 confirms.
- Search by patient, MRN, name or registration number.
- Joins, lookups or links to clinical tables or clinical endpoints, including links to patient history, orders, test runs or the MRN search.
- Finalisation, delivery, SIMRS sync or any other workflow action.
- Any write method.
- Returning deviations, fragments or unparseable messages.

### C.1 Navigation and component boundary

- **The view.** A new view, **"Unlinked instrument results"**, is added as a new state of the router-less `App.tsx` shell.

- **Worklist link.** When the selected instrument's order worklist is empty and unlinked results exist for it, the worklist empty state **MAY** link to the new view with the neutral text "Unlinked instrument results". This is an additive text change only.

  - `Pagination`, `LoadingState`, `ErrorState` and `EmptyState`;
  - the `dateRange.ts` helpers;
  - `DateRangeFilter`, **only** with a caller-supplied neutral caption for its "All" preset. Today it shows "All dates · every order for this instrument"; the caption becomes an optional prop whose default keeps the M8.4 text unchanged.
- **Not reusable for XN-550 data:**
  - `ResultTable` and `ResultRow` — typed on the clinical `ResultResponse`;

- **Placement of new code.** New XN-550 components live in their own folder (for example `components/instrument-results/`) and import no clinical type.

### C.2 List view

- **Identity disclaimer.** Persistent, non-dismissible, always rendered at the top of the view, and keyed to `identity_notice`. The exact text, shared with C.3:

  > Not linked to any patient record. The Sample No. is text typed on the instrument and is not a verified patient or specimen identity. These results are not screened for QC material, cannot be finalised and are not sent to SIMRS.

  This is the pinned default that OD-XN-3.3 confirms.
- **Controls:** the date range (C.1 rule) and the instrument selection only. There is **no** search box, **no** Sample No., patient, MRN or name field, and **no** sort control.
- **Columns — the complete list:**

| Column | Content |
|---|---|
| Received (LIS time) | `received_at` |
| Analysed (instrument clock) | `analysis_at` |
| Sample No. (as entered on instrument) | `sample_label` |
| Instrument | `instrument_name` |
| Items with instrument flag other than N | `non_n_flag_item_count` |
| Notes | Badge **"Possible duplicate of #N — same content, not verified as the same analysis"**, linking to `possible_duplicate_of`, when `POSSIBLE_DUPLICATE`. Badge **"Delivered N×"** when `delivery_count > 1` |

- **Never shown:** `r_sequence`, the hash prefix, session ids.
- **Rows** are never grouped, merged, collapsed or visually linked by Sample No., session or delivery.
- **Shared components:** `Pagination`, `LoadingState`, `ErrorState` and `EmptyState`.

### C.3 Detail view

- **Header:** Received (LIS time), Analysed (instrument clock), Sample No. (as entered on instrument), Instrument, the duplicate badge and the delivery count.
  - **No** `r_sequence` or "Seq" value.
  - **No** patient, visit or order field.
- **Identity disclaimer:** the C.2 text, persistent and non-dismissible, above the results.
- **Result table.** An XN-550-specific component, never `ResultTable` or `ResultRow`, with the columns Parameter (`test_code`) · Value (verbatim) · Units (verbatim, "—" when null) · Reference range (always "—"; never computed) · Instrument flag.
- **Grouping by `item_kind`:**
  - Measured parameters.
  - Instrument interpretive messages — the score is shown verbatim with the caption "meaning not verified". This is the design default that OD-XN-3.2 confirms or changes.
  - Instrument flags (name and flag).
  - "N graphics referenced on the instrument (not transferred)" — test codes only, never a path.
- **XN-550 flag presentation (API-3 closure).** It uses an exact, case-sensitive match on the verbatim value, with no trimming, case folding or prefix matching:

| `abnormal_flag` | Presentation | Accessible label |
|---|---|---|
| null | "—" | "No instrument flag" |
| Exactly `H` | ▲ H, high-flag colour token | "Instrument flag H: high (ASTM E1394 code)" |
| Exactly `L` | ▼ L, low-flag colour token | "Instrument flag L: low (ASTM E1394 code)" |
| Exactly `N` | ✓ N, normal-flag colour token | "Instrument flag N: normal (ASTM E1394 code)" |
| Anything else — `A`, `W`, lower-case letters, words such as `HIGH`, `LOW`, `NORMAL`, `WARNING` or `CRITICAL`, values with spaces | "?" followed by the verbatim value, neutral colour | "Instrument flag «value»: meaning not verified" |

  - **Known / unknown split unchanged:** only `H`, `L` and `N` are known, and `A` / `W` stay unknown (§7.5; OD-XN-3.2 confirms their display).
  - **A constant of the XN-550 component.** It does not use `ResultFlag` or its mapping, and it is not derived from the parser's observed-value sets or novelty tokens. Novelty warnings stay a backend log concern and never change the presentation.
  - **Adding a known value** requires a contract change backed by field evidence (§8.3). No meaning is ever invented for an unknown flag.
- **Provenance panel**, collapsed by default:
  - the deliveries (received time, session id, read count);
  - parser key and version, the SHA-256 prefix, raw length and ACK policy;
  - never an IP address, a port, the full hash or raw content.
- **No links or workflow controls.** There is no link to patient history, orders, test runs or the MRN search, and no Final Run or SIMRS control.
