# **M8.5 INVESTIGATION**

## **1\. Executive Verdict**

**M8.5 is ready for implementation. No backend change is required.** The M8.4 contract supplies every field the intended UX needs, including `id_visit` — which turns out to be the key that makes detail reuse work without duplication.

The frontend architecture supports M8.5 with **one mandatory refactor**: extracting the detail body out of `App.tsx` (388 lines, all detail state and rendering inline). Without it, M8.5 will duplicate clinical detail — the single largest risk.

**Decisions that must be frozen before coding:**

1. **No React Router.** `frontend/package.json` has exactly two runtime dependencies (`react`, `react-dom`). State-based view switching is sufficient and consistent.  
2. **Sidebar replaces `StickyStatusBar`.** Both render all instruments from the same endpoint; keeping both duplicates instrument navigation and status UI.  
3. **Instrument identity comes from `GET /api/instruments/status`.** The PoC's hardcoded string IDs (`'bc5150'`, `'bs240'`) are fabricated and reference instruments that do not exist in the current seed. They must not be copied.  
4. **Drill-down must preselect `id_visit` *and* `id_order`.** Preselecting the order alone is silently overridden by an existing effect in `App.tsx:154-172`.  
5. **Overview is a compact row list, not a clinical table.** M8.4's grain is one Order; the PoC's parameter-level grid is a different grain entirely.  
6. **PoC visual values are not adopted.** The current branch already has the enterprise palette in `index.css:3-36`; the PoC uses a different (slate) palette that would create a second design system.

## **4\. Navigation Decision**

**State-based view switching in `App.tsx`. No React Router.**

Evidence: zero router dependency (`package.json:12-15`); the product needs exactly two views; there is no stated deep-link, bookmark, or back-button requirement anywhere in the repository or the task list. Adding `react-router-dom` would introduce a dependency, a provider, a route table and a `useNavigate` indirection to switch between two components.

App  
 │  activeInstrumentId : number | null      ← Sidebar click  
 │  detailTarget       : { nomorRm, idVisit, idOrder } | null  
 │  
 ├─ Sidebar (always visible)  
 │     onSelect(id) → setActiveInstrumentId(id); setDetailTarget(null)  
 │  
 └─ MainContent  
      detailTarget \=== null  
        → \<OrderOverviewView instrumentId={activeInstrumentId} onOpenOrder={setDetailTarget} /\>  
      detailTarget \!== null  
        → \<OrderDetailView {...detailTarget} onBack={() \=\> setDetailTarget(null)} /\>

**Why `detailTarget` is an object, not a bare `orderId`:** the existing detail is driven by the patient-history tree. `App.tsx:154-162` resets `selectedVisitId` to the newest visit whenever the current one is absent, and `:164-172` then resets `selectedOrderId` to the first order *of that visit*. Passing only an order id from a non-newest visit would be silently overridden. M8.4 returns `nomor_rm`, `id_visit` **and** `id_order` on every row, so all three travel together.

**Back navigation:** an explicit "← Back to worklist" control. Overview state (instrument, dates, page) lives in `App`, so returning restores the exact list without a refetch of state.

## **6\. Overview UX Decision**

**Recommendation: a semantic `<table>` styled as a compact worklist — a hybrid, not a card grid and not a dense clinical grid.**

Why a table rather than cards: the rows are homogeneous, column-aligned scanning is how a worklist is actually used ("which of these has abnormals?"), and `<table>` gives screen-reader row/column semantics for free. Why *styled as a worklist*: the user explicitly wants patient name as the visual anchor, not a spreadsheet.

Cards were rejected because they cost roughly 2–3× the vertical space per row, which matters at `page_size = 50`, and they break column alignment for the status/abnormal signals.

**Row structure — 5 columns:**

| Column | Content | Treatment |
| ----- | ----- | ----- |
| **Patient** | `nama_lengkap` (**0.95rem, weight 600** — the anchor)\<br\>`nomor_rm` · `no_registrasi` (0.75rem, `--color-text-secondary`, monospace) | Two-line cell; \~40% width |
| **Order time** | `waktu_order`, `dd/MM HH:mm` | `--font-clinical`, right-aligned |
| **Status** | `status_order` text; `is_final` badge when true; `delivery_status` badge when non-null | Small pill badges |
| **Abnormal** | `abnormal_count` | `0` → muted "—"; `> 0` → count in `--color-flag-high` with an icon **and** text label (matching the M7 accessibility rule: never colour alone) |
| **(chevron)** | `›` | `aria-hidden`, affordance only |

Row height \~56px (two-line patient cell). Hover → `--color-surface-hover`. No horizontal scroll at ≥1024px; wrap the table in `overflow-x: auto` for safety.

## **8\. Filter / Date Design**

**Controls.** Two `<input type="datetime-local">` fields labelled "From" and "To", plus three quick presets: **Today** (default), **Yesterday**, **Last 7 days**.

**Frontend defaults — explicitly a frontend-only convention, not API semantics:**

date\_from \= today 00:00:00 (browser local)  
date\_to   \= tomorrow 00:00:00 (browser local)   ← half-open, matches \[from, to)

**Server-local naive handling.** The API documents both parameters as server-local naive and instructs clients not to send an offset. `datetime-local` yields exactly `YYYY-MM-DDTHH:mm` with no zone, so the value is sent **verbatim** — no `toISOString()`, no `Date.prototype` conversion, no `Z` suffix. This is the single most important implementation constraint in the date layer: `toISOString()` would shift every boundary by the UTC offset (−7h for WIB) and silently show the wrong day.

**Validation.** Disable submit and show inline "To must be after From" when `date_to <= date_from`; do not issue the request. The API also returns 422, which is handled as a fallback.

**Loading.** Keep the previous rows visible with reduced opacity plus a "Refreshing…" `role="status"` line — the pattern already used at `App.tsx:319-323`.

**Page reset.** Any change to instrument, `date_from`, or `date_to` resets `page` to 1 — the one PoC pattern worth reusing (`poc/mindray:App.tsx:51-53`).

## **9\. Pagination Design**

Offset/limit only, consuming `{page, page_size, total}` as returned.

* **Controls:** `‹ Previous` / `Next ›` buttons plus "Showing X–Y of Z". `Previous` disabled at `page === 1`; `Next` disabled when `page * page_size >= total`.  
* **No page-number list.** Total page count is derivable, but a worklist is scanned sequentially; numbered pages add UI for no workflow benefit.  
* **`page_size`:** fixed at **25** for M8.5 (below the API's `le=100`). Not user-selectable in this milestone.  
* **Reset:** on instrument change, on date change, and on returning from detail only if filters changed.  
* **Empty:** `total === 0` → `EmptyState` "No orders for this instrument in the selected period", with the date range echoed. Pagination controls hidden.  
* **Loading:** buttons disabled during fetch.  
* **Error:** `ErrorState` with `onRetry` — the existing component, which already accepts `error`, `message`, `onRetry`, `title`.

## **18\. Risks**

| \# | Risk | Impact | Mitigation |
| ----- | ----- | ----- | ----- |
| **R1** | **Duplicate clinical detail.** Building a second detail view instead of extracting the existing one | Two divergent implementations of finalisation and SIMRS sync — the highest-consequence failure available | §10 extraction is step 1 of the plan and must land **before** any overview work; test \#12 |
| **R2** | **Preselected order silently overridden.** Passing only `id_order` lets `App.tsx:154-172` reset to the newest visit's first order | User clicks patient A's order and lands on a different one. | **R3** | **Date offset via `toISOString()`.** The API demands server-local naive strings | Every boundary shifts by the UTC offset (−7h WIB); "today" shows the wrong day's worklist | Send `datetime-local` values verbatim; never construct a `Date` for transport (§8); test \#3 |

| **R5** | **Stale page/detail on context switch.** Forgetting a reset when instrument or dates change | Empty page 3 after switching instrument; detail from a previous instrument still open | Explicit resets in `App` (§8, §9); tests \#4, \#5 |
